# Личные подключения Confluence и Jira

Подключение необязательно и действует только для выбранного локального проекта. Включите модуль «Confluence и Jira», выберите сервис и размещение, укажите HTTPS-ссылку на существующую страницу Confluence или Jira-проект, затем личные учётные данные. До успешного чтения указанного корня подключение не считается проверенным. Наличие ссылки или файла настроек не означает рабочее соединение.

| Размещение | Авторизация | Пример ссылки |
|---|---|---|
| Atlassian Cloud, личный режим | Email Atlassian и classic API token; явное согласие на личное подключение | `https://team.atlassian.net/wiki/spaces/DOC/pages/123/Architecture`, `https://team.atlassian.net/jira/software/c/projects/APP/boards/1` |
| Confluence Data Center | Personal Access Token, `Authorization: Bearer …` | `https://docs.company.example/confluence/pages/viewpage.action?pageId=123` |
| Jira Data Center | Personal Access Token, `Authorization: Bearer …` | `https://jira.company.example/jira/projects/APP` |

Cloud API tokens со scopes, использующие `api.atlassian.com/ex/...`, не являются classic-токенами прямого адреса сайта и этим режимом не поддерживаются. Пароль аккаунта не запрашивается. Data Center требует версии с PAT: Confluence 7.9+ / Jira 8.14+. Сертификат HTTPS должен проверяться системным доверием; режим отключения TLS-проверки отсутствует. Частные адреса внутренней сети, context path и HTTPS-порт вроде 8443 поддерживаются. HTTP, localhost, loopback, link-local и адреса метаданных запрещены.

**Граница Cloud:** это локальный личный REST-коннектор, не реализация vendor OAuth и не заявление о соответствии требованиям распространяемых Atlassian Cloud apps. Atlassian рекомендует зарегистрированное единое OAuth 3LO-приложение для распространяемых интеграций и ограничивает сбор пользовательских API tokens такими приложениями. Настоящее публичное OAuth-подключение потребует регистрации приложения и доверенного broker/callback; client secret нельзя встраивать в VSIX. См. [официальные требования к Cloud-аутентификации](https://developer.atlassian.com/cloud/jira/platform/basic-auth-for-rest-apis/).

## Что отправляется

Синхронизация односторонняя: DashAI → выбранный сервис. Отправляются описание проекта и состав документа, описания файлов, схемы архитектуры и включённые текстовые модули. Выключенные «Карта проекта», «Архитектура», «Документация» и пользовательские модули исключают соответствующий материал из будущих отправок. Код исходных файлов, локальные credentials и произвольные файлы компьютера не читаются. Задачи Kanban в этой версии не экспортируются в Jira.

Каждое описание получает отдельный стабильный локальный ключ: `project`, `file:<path>`, `diagram:<id>`, `module:<id>`. Remote mapping хранится отдельно для Confluence и Jira; переименование заголовка не создаёт вторую запись. Изменение пути файла представляет новую запись карты. Заголовок и тело содержат идентификатор происхождения DashAI. Не удаляйте его, если собираетесь продолжать автоматическую синхронизацию.

Confluence получает текст в безопасном storage-формате, Jira Cloud — Atlassian Document Format, Jira Data Center — текст. Mermaid публикуется исходником вместе с нотацией, объяснением и легендой. Для нативной отрисовки Mermaid в Atlassian может потребоваться отдельное приложение; DashAI не устанавливает сторонние macros. Описание более 30000 символов не обрезается молча: Jira-отправка получает явную ошибку, текст нужно сократить или разделить на локальные модули.

## Жёсткая граница назначения

- В Confluence создаются только непосредственные дочерние страницы указанной корневой страницы в её проверенном пространстве. Сам корень не перезаписывается. Создание пространства, перенос страниц и запись в соседние ветки отсутствуют.
- В Jira создаются обычные задачи только в проверенном проекте по его numeric ID. «Подпроект» DashAI не становится новым Jira-проектом: Jira не предоставляет такую вложенность проектов. Тип обычной задачи выбирается из доступных типов проекта; custom fields, обязательные именно в вашем workflow, могут потребовать другой тип или отдельную настройку Jira.
- Перед каждой отправкой повторно читается корень. Перед обновлением читается remote page/issue и проверяется его принадлежность. Если запись вручную перенесли за разрешённую границу, обновление блокируется.
- Адрес сервера, размещение и идентичность корня закрепляются первым подключением, включая период после отключения. Для другого назначения используйте отдельный локальный проект. Отключение не удаляет опубликованные материалы.

## Автоматическая отправка, повторы и конфликты

Сохранение локального описания, его audit и постановка в outbox происходят в одной SQLite-транзакции. HTTP-запись в Atlassian не может быть общей атомарной транзакцией с локальной SQLite. Поэтому UI показывает очередь и результат, а не выдаёт локальное сохранение за завершённую удалённую публикацию.

Фоновый работник делает паузу 5 секунд между проходами и отправляет до 10 записей за проход. Выключенные подключения и модули отфильтровываются до ограничения очереди и не задерживают другие проекты. Сетевая операция не держит SQLite write transaction. Изменение одного подключения блокирует только его собственную отправку; чтение статусов и работа в остальных проектах доступны.

| Статус | Значение и действие |
|---|---|
| `pending` | Есть локальная версия для отправки |
| `processing` | Выполняется подтверждённая попытка отправки |
| `synced` | Удалённая запись подтверждена и mapping сохранён |
| `failed` | Ошибка прав, лимита, сети, формата либо конфликт; повтор с паузой от 30 секунд до часа |
| `uncertain` | Создание могло состояться, но ответ не подтверждён; сначала выполняется поиск по идентификатору происхождения |
| `removed` | Материал выключен или исчез из локальной карты; удалённая запись сохраняется |

Неопределённый POST никогда не повторяется вслепую. Точный снимок исходной отправки сохраняется до сетевого запроса. Если remote запись найдена, её управляемые поля сверяются с этим снимком: правка человека не становится автоматически разрешением её перезаписать. Если поиск пока не видит запись, статус остаётся неопределённым. Выключение/повторное включение локального модуля сохраняет эту неопределённость, включая изменение текста. Прерванная отправка восстанавливается так же после перезапуска.

Если материал вручную изменён в Atlassian, DashAI останавливает его обновление. Сначала сверьте версии и сохраните нужные удалённые дополнения в локальном описании. API допускает явную подтверждённую перезапись управляемого документа через `overwrite_remote: true`. Confluence дополнительно проверяет optimistic page version. Jira REST не даёт общей атомарной compare-and-swap для всех полей: между чтением описания и PUT остаётся внешняя конкурентная гонка, поэтому не редактируйте один управляемый документ одновременно в двух приложениях.

Если после неопределённой отправки человек проверил удалённый проект и достоверно установил отсутствие документа, `/resolve` с `confirm_remote_absent: true` разрешает новое создание. Это явное действие с причиной и version, а не автоматическое решение по пустому поисковому индексу.

## API и хранение

Настройка, отправка, отключение и разрешение неопределённости доступны только человеку. HTTP/MCP-публикация знаний проходит общий domain/API и автоматически ставит разрешённую отправку в ту же outbox.

| Метод и путь после `/api/projects/{project_id}/integrations` | Поля |
|---|---|
| `GET` | Публичные настройки, проверенный корень, `credential_present`, счётчики и до 20 безопасных ошибок |
| `PUT /{confluence\|jira}` | `expected_version`, `reason`, `url`, `deployment: cloud\|data_center`, `email?`, `token?`, `personal_cloud_token?`, `enabled?`, `auto_sync?`, `issue_type_id?` |
| `POST /{provider}/sync` | `expected_version`, `reason`, `overwrite_remote?: false` |
| `POST /{provider}/disconnect` | `expected_version`, `reason` |
| `POST /{provider}/resolve` | `expected_version`, `reason`, `local_id`, `confirm_remote_absent` |

У нового подключения `expected_version: 0`. При 409 перечитайте состояние; автоматического overwrite по старой версии нет. Пустой `token` при обновлении сохраняет существующий секрет; после отключения требуется ввести его заново. Повторный connect со старой версией не создаёт второе подключение. Manual sync действует на выбранный provider; включённый `auto_sync` — на будущие изменения разрешённых описаний.

Credentials сохраняются отдельным атомарно заменяемым файлом `integration-secrets/<connection-id>.json` внутри личной папки данных, с POSIX правами 0700/0600. На Windows действует ACL личной папки ОС. Email и token не попадают в SQLite, audit, idempotency, read API или экспорт. При отключении credential-файл удаляется, mappings и локальные тексты сохраняются. Локальный пользователь ОС, имеющий доступ к папке данных, входит в доверенную границу продукта.

SQLite-таблицы: `integrations` — безопасные настройки; `integration_outbox` — текущая версия/статус отправки; `integration_mappings` — подтверждённые remote IDs и версии; `integration_attempts` — исходный снимок неразрешённого создания. Raw remote bodies, URL с секретами, пароли и токены не включаются в сообщения ошибок. Redirects и environment HTTP proxy выключены; credentials отправляются только проверенному HTTPS origin.

Проверка реализации: `.venv/Scripts/python.exe -m pytest tests/test_integrations.py -q`. Тесты используют `httpx.MockTransport` и изолированные временные данные: обе редакции, оба сервиса, scope, конфликты, неизвестный POST, восстановление, fairness, module gate, sanitization и отсутствие секретов. Без действительного пользовательского URL и credentials live Atlassian-подключение не проверялось.
