# DashAI 1.4: независимая проверка подпроектов

Дата: 04.10.2026. Отдельный критик `dashai_critic`; реализацию API/MCP написал `subprojects_backend`, UI — основной агент. Прочитаны контракт архитектуры, исследования и Ponytail full/review. Проверка относится к вложенности подпроектов на одной общей Kanban-доске, а не к созданию отдельных досок.

## Замечания и исправления

1. **Idempotency различает «сохранить принадлежность» и «очистить принадлежность».** В первоначальной реализации `model_dump()` превращал пропущенные `subproject_id`/`parent_id` в `null` при сравнении повторов PATCH. Поэтому retry с тем же ключом, но измененным намерением мог получить прежний успешный результат вместо 409. Критик передал finding автору. Исправление сохраняет presence нового nullable поля в task PATCH и использует `exclude_unset` для нового subproject PATCH. Старые cached запросы 1.3 остаются совместимыми; explicit null теперь отличается от отсутствующего поля. Добавлены проверки повторов в обе стороны и сохранения текущего родителя/группы.
2. **Legacy section ID не может притворяться принадлежностью подпроекту.** Первоначально task `section_id` принимал `kind=subproject`, хотя board/export показывают подпроекты в отдельной коллекции. По замечанию критика общая `validate_task` теперь отклоняет такое значение и требует `subproject_id`; соответствующая проверка есть для create и patch. Старые настоящие section ID работают.
3. **Фильтр подпроекта очищается при смене проекта.** Первоначальная версия сохраняла UUID подпроекта A при переходе на доску B; dropdown не имел соответствующей option, а все задачи B исчезали. Основной агент добавил очистку в effect `projectId`, покрывающем все пути переключения проекта. Независимый browser smoke двух проектов подтвердил исправление.
4. **Конфликт редактирования подпроекта объясняет повторное чтение.** Modal хранит исходную version, поэтому нельзя просто отправлять форму снова после 409. Основной агент добавил явное сообщение: сохранить нужные правки, закрыть форму, обновить доску и открыть объект повторно. До закрытия введенный текст остается в форме; server version guard не снимается и overwrite не повторяется автоматически. Это простой ручной повтор с актуальной version, без speculative merge UI.
5. **Исправлены мобильные действия на 320 px.** При независимом просмотре `artifacts/qa/dashai-subprojects-mobile.png` новая кнопка «Подпроект» оказалась частично за левым краем viewport: три действия не помещались в nowrap строку с `justify-content: flex-end`. Проверка ширины документа этого не ловила, потому что выход был в отрицательные координаты. По замечанию критика добавлен native CSS `flex-wrap: wrap` и проверки реальных left/right bounding rect каждой кнопки на 1440/390/320 px. Критик повторно запустил браузерный smoke и просмотрел новый screenshot: названия и действия полностью доступны, кнопки корректно перенесены.

## Прочитанный контракт

Подпроекты хранятся как явно помеченные JSON entities существующего SQLite store; legacy sections не превращаются в подпроекты. Task grouping — отдельное nullable поле, независимое от task type, status и legacy section FK. Чтение старых задач дает `subproject_id: null` без переписывания исходных строк и истории.

Create/update подпроекта, version check, обход родителей, запись entity и audit выполняются в одной `BEGIN IMMEDIATE` транзакции. Самоссылка, цикл, чужой проект и legacy section в качестве родителя отвергаются. Два параллельных изменения `A → B` и `B → A` сериализуются; оба не могут успешно образовать цикл. Перенос подпроекта меняет контекст всех его потомков, сохраняя task IDs, статусы и историю.

MCP использует тот же HTTP API. `create_subproject`/`update_subproject` принимают reason, idempotency key и fresh version; `get_board` и `ready_tasks` умеют фильтровать поддерево или только выбранный уровень. Результаты остаются bounded; для подпроектов добавлены отдельные pagination offsets и context. Session ID записывается в audit; наличие конфига не выдается за активное подключение агента.

UI содержит одну доску с пятью статусами. Подпроект выбирается native select при создании/редактировании карточки, путь виден на карточке и в detail; раскрываемый список подпроектов предлагает вложенное создание/редактирование и считает задачи потомков. Родительский select исключает сам подпроект и его потомков; API повторно проверяет это независимо от UI. Native `details`, `select`, подписанные icon buttons и существующий native dialog сохраняют клавиатурный путь. Длинные пути переносятся через `overflow-wrap: anywhere`; фактический mobile reflow подтвержден повторным browser smoke и просмотром screenshot.

## Проверки

После обоих backend исправлений критик самостоятельно выполнил `.venv-build/Scripts/python.exe -m pytest tests/test_api.py tests/test_mcp.py -q`: **18 PASS**, 24.36 секунды. Проверены трехуровневая вложенность, принадлежность/переназначение карточки, nullable idempotency семантика, перенос родителя, before/after и session в audit, экспорт/перезапуск, legacy cached retries без переписывания истории, rollback запрещенных ссылок и конкурентный цикл. Реальный MCP SDK сценарий поднимает два stdio клиента, использует общий HTTP API, параллельно занимает разные карточки Codex/Claude, фильтрует поддерево и сохраняет session в истории. Bounded output проверен с 500 подпроектами и длинными описаниями. Предупреждения исходят от внешних библиотек Python 3.14 и не скрыты.
