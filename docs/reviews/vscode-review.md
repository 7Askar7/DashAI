## Обнаруженные ошибки

1. **P1, `vscode-extension/extension.cjs:107`: ответ extension host теряется.** HTML-мост принимает `agentboard-host-result` только при `event.source === window`. VS Code пересылает сообщение из своего preload iframe в content iframe; источником события является окно preload, а не окно получателя. В результате clipboard/export выполняются в host, но UI не получает подтверждение и ждет timeout. Требуется проверка origin host-сообщения с сохранением отдельной проверки источника и origin для сообщений доски. Обязательная повторная проверка — настоящий VS Code, копирование и JSON export через оба направления моста. Основание: [Microsoft: пересылка host message](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/webview/browser/pre/index.html).
2. **P1, `src/host.ts:3`: неверное распознавание webview origin.** Regex разрешает только hex/дефисы, но современный VS Code кодирует authority webview как 52 символа base32 SHA-256 (цифры и `a-v`). Desktop использует `vscode-webview://` с этим authority. Значит `insideVSCode` становится false, а UI использует браузерный download/clipboard вместо native host bridge. Следует проверить реальное `ancestorOrigins` в редакторе и разрешить точный подтвержденный формат; произвольный parent origin допускать нельзя. Основание: [Microsoft: вычисление origin](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/webview/browser/pre/index.html), [Microsoft: webview endpoint](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/webview/browser/webviewElement.ts).

Обе ошибки переданы основному агенту до упаковки окончательного VSIX. Исправления кода перечитаны критиком: host replies принимаются только с точным собственным webview origin и не от localhost iframe; исходящие сообщения доски по-прежнему требуют точный iframe source и localhost origin. `host.ts` принимает только два подтвержденных desktop формата authority: legacy 36 символов и современный base32 52 символа.

Критик дополнительно поймал недостаточность промежуточного исправления `event.source === window.parent`: Microsoft injected SDK маскирует `window.parent = window`. Независимый Chromium эксперимент в настоящем вложенном iframe подтвердил: сохраненный реальный parent отличается от самого окна, а после такого присваивания `window.parent === window` становится true. Поэтому parent equality удалена именно на границе host → webview; проверка собственного уникального origin сохранена. Настоящий editor smoke после исправлений подтвердил оба направления clipboard/export; findings закрыты.

## Дополнительная проверка обновления MCP

Критик выявил отдельный разрыв обновления: сохраненные project configs указывают на постоянный, но версионный `vscode-runtime/1.4.0/AgentboardMCP.exe`. Установка нового VSIX сама по себе не меняет этот command. Для требования автоматического обновления агентов добавлен короткий native forwarder: старый frozen companion при следующем запуске следует подтвержденному более новому runtime, сохраняя существующий config. Source mode и явный `--url` не перенаправляются.

Перечитана реализация `forwarding_target` и native handoff. Допускается только старый executable в точной личной version folder, target в той же personal data folder с корректной более новой трехкомпонентной версией, совпадающим package marker и без symlink escape. Runtime descriptor проверяется против ограниченного 16 KiB public health ответа: instance UUID, PID, версия, режим и boolean MCP state. Probe не отправляет credentials и не следует proxy/redirect. Original arguments, относительные пути и CWD клиента, actor/session и exit code сохраняются; новый companion своей текущей версии повторно не перенаправляется. Для нового top-level PyInstaller процесса предусмотрены DLL reset и `PYINSTALLER_RESET_ENVIRONMENT=1` — [официальная документация PyInstaller](https://pyinstaller.org/en/stable/advanced-topics.html).

**P1, native handoff: Windows stdio handles — исправлен и закрыт.** Первый настоящий frozen fixture запустил правильный child, но MCP initialize завис. Unit tests этого не выявляли. Критик независимо прочитал локальный Python 3.14 `subprocess` source и воспроизвел проблему реальным Windows трехпроцессным probe: `CREATE_NO_WINDOW` с omitted stdin/stdout/stderr не передает client streams явно; child не вернул ответ и завершился по ограничивающему watchdog. Та же команда с `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` вернула точный ввод и exit code 0. Это прямые родительские handles без PIPE/relay. Основание: [Python subprocess: file objects и Windows handle inheritance](https://docs.python.org/3/library/subprocess.html). Finding передан основному агенту и автору connector до выпуска; исправление подтверждено повторным настоящим frozen fixture.

Исправление с тремя explicit parent streams перечитано критиком; соответствующие две forwarding tests самостоятельно повторены: **2 PASS / 3.03 s**. Независимый повтор API/MCP/desktop suite до исправления handles: **25 PASS / 24.43 s**. Эти результаты не выдаются за доказательство native forwarding. Скрипты `vscode_smoke.py`, `vscode_handoff_smoke.py` и `actual-driver.cjs` проверены отдельно: изолированы profile, extensions, personal data и mutex username; native SaveDialog stub ограничен API проверяемого extension, восстанавливается вместе с clipboard; HTTP cleanup использует только QA runtime и instance proof, process termination — собственный Popen. WinCIM читает только два точных fixture EXE paths. Версия нового fixture изменяет только bundled package metadata текущего build; проверка не заявляет существование будущего release.

Повтор настоящего frozen handoff **PASS, exit 0**, evidence `artifacts/qa/vscode-handoff-087a3d3f82/results.json`: Windows inventory показывает старый companion PID 47400 и новый child PID 142876 с точным parent PID. MCP SDK initialize и инструменты реально работают через исходные client pipes; task и subproject созданы в общем API, actor/session сохранены, после stdin EOF child завершился и MCP handle освобожден. Критик независимо просмотрел results/runtime/stderr и проверил read-only SQLite: одна карточка, один подпроект, правильная связь, все audit events с Codex и исходным session, `integrity_check=ok`, нет SQLite копий в обоих runtime directories.
