# DashAI: потребности пользователей и UX-аудит

Дата: **18 октября 2026 года, Москва**. Исследование проведено для запроса «что добавить, убрать, доработать и как улучшить дизайн и UX/UI».

## Главный вывод

Наиболее обоснованное направление DashAI — помогать человеку **выбирать следующий шаг, проверять результат агента и восстанавливать контекст**. Уже существующие общая доска, причины изменений, evidence, карта проекта и локальное хранение соответствуют этому направлению. Следующий прирост удобства ожидается от лучшей организации этих данных: очередь внимания, последовательные фильтры, понятное состояние проверки и спокойная рабочая поверхность.

Это проектный вывод из источников и аудита реализации, а не установленное предпочтение всех пользователей. На 18 октября нет проведённых нами интервью, аналитики использования DashAI, тестов с целевыми пользователями или измеренного роста продуктивности. Поэтому документ разделяет подтверждённые факты, экспертные выводы и проверяемые гипотезы.

## Метод и границы

Изучены [контракт архитектуры](../architecture.md), README, исследования [01](01-products.md), [02](02-agent-needs.md), [03](03-ux-ui.md), [04](04-marketplace-packaging.md), [05](05-large-project-map.md), [06](06-atlassian-sync.md), [07](07-project-modularity.md), основные потоки `src/App.tsx` и `src/KanbanBoard.tsx`. Исторические исследования отражают прежние этапы продукта: актуальная модель — проект → необязательные вложенные подпроекты → задачи на общей доске. Рекомендация раннего исследования о обязательной секции не переносится в текущий интерфейс.

Новые внешние источники открыты непосредственно 18.10.2026. Использованы исследования их авторов, официальная документация продуктов, W3C и design systems; поисковые пересказы и рекламные обещания не служат доказательством. Сравнение аналогов описывает механизмы, а не результат их независимого тестирования.

Уровни основания:

- **Наблюдение реализации:** видно в прочитанном коде или контракте. Это подтверждает устройство интерфейса, но не частоту проблемы и не прохождение браузерной проверки.
- **Наблюдение исследования:** результат конкретной выборки с её ограничениями. Пользователи этих исследований не являются автоматически пользователями DashAI.
- **Вывод:** наше объяснение, почему наблюдение важно для DashAI.
- **Гипотеза:** ожидаемый эффект изменения, который нужно проверить на людях.

Ни количество событий, ни наличие конфигурации, ни текст evidence не доказывают работающую сессию, запуск теста или принятие результата. MCP проекта при исследовании возвращал 401; содержимое реальной доски не использовалось для оценки пользовательского поведения. Отчёт не содержит credentials или частных данных.

## Роли и задачи пользователя

Это рабочие сегменты для набора участников исследования, а не измеренные доли аудитории. Один владелец локального пространства может выполнять все роли.

| Роль | Работа, которую нужно выполнить | Что мешает | Признак успеха |
|---|---|---|---|
| Разработчик, ведущий несколько внешних агентов | Вернуться к проекту и выбрать, что проверить или разблокировать | Контекст рассыпан между чатами, доской и репозиторием | Находит нужную задачу и объясняет следующий шаг без чтения всей ленты |
| Проверяющий результат, включая самого автора проекта | Понять изменение, увидеть критерии и основание завершения | Слово «готово» выглядит сильнее приложенных свидетельств | Отличает сообщение агента от независимой проверки и принимает осознанное решение |
| Новый пользователь MCP | Создать первый полезный результат и убедиться в связи клиента | Имя исполнителя, формат конфигурации и контакт с API легко спутать | Выполняет реальный тестовый запрос и находит созданную задачу |
| Пользователь, возвращающийся в большой проект | Найти назначение файла и прошлую причину решения | Длинное дерево, устаревшие описания, много событий | Находит объяснение и понимает, к какому снимку оно относится |
| Пользователь с узким webview, увеличением или клавиатурой | Выполнить тот же workflow в ограниченном пространстве | Горизонтальный поиск колонок, обрезанные действия, потеря фокуса | Создаёт, находит, проверяет и перемещает задачу без обязательного drag |

DashAI остаётся локальным пространством одного пользователя ОС. Эти роли не означают, что уже существуют многопользовательские права, командный SaaS или защищённое внешнее ревью.

## Аудит входного состояния

Ниже — срез исходного интерфейса **до изменений этого аудита**. Ссылки относятся к компонентам, поскольку параллельная доработка меняет номера строк. Наблюдения основаны на статическом чтении; итоговую визуальную и функциональную проверку нужно читать в отдельном отчёте реализации.

| Наблюдение | Почему стоит доработать | Что уже сделано правильно |
|---|---|---|
| `App`: счётчики «в работе / на проверке / блокировки» являются текстом | Пользователь видит сигнал, но не получает прямого действия по нему | Счётчики вычислены из настоящих задач |
| `App`: статусный фильтр применяется только при `listView`; в режиме доски это условие исчезает | Одна смена представления меняет множество результатов; нужно повторно ориентироваться | Поиск и остальные фильтры уже комбинируются; есть сброс и пустая выдача |
| `App`: `v{project.version}` на проекте и `v{task.version}` в списке | Техническая версия записи похожа на выпуск продукта, особенно после появления модуля релизов | Версии необходимы серверу для защиты от конфликтов |
| `App`: первые четыре нечеловеческие идентичности из общего каталога показаны в шапке каждого проекта | Визуально могут считываться как работающие в выбранном проекте агенты | Экран подключения отделяет identity от формата клиента |
| `TaskDrawer`: evidence находится среди всех записей, затем идёт полная хронология | При длинной задаче основание завершения приходится искать среди прогресса и комментариев | Уже есть типы evidence/change/decision, автор, время и артефакты |
| `KanbanBoard`: каждая карточка содержит отдельную строку перемещения | На насыщенной доске служебные действия конкурируют с результатами задач | Это доступная альтернатива drag; её нельзя просто удалить |
| `EntityForm`: первый экран содержит подпроект, тип, описание, rationale, критерии, исполнителя, приоритет и reason | Для простого первого действия нужно осмыслить много полей; причина события и цель задачи похожи по формулировке | Поля подписаны; критерии объяснены; зависимости уже раскрываются отдельно |
| `App`: несколько информационных полос до самой доски, функциональные модули в одной строке навигации | В узком webview рабочим карточкам остаётся меньше места | Модули уже можно выключать без удаления данных |

Это не оценка «проект плохой». Основные domain-механизмы уже защищают важные пользовательские интересы: общий HTTP-контракт, атомарный audit, conflicts вместо overwrite, явный reason, сохранение документов при отключении модулей, evidence gate и отсутствие ложного online. Их нужно сделать понятнее и заметнее, сохранив поведение.

## Что добавить, убрать и доработать

Приоритет P0 — ближайшая итерация удобства; P1 — следующий проверяемый шаг; P2 — только после подтверждения сценария. «Малая» стоимость означает локальное изменение представления существующих данных; «средняя» — новый поток или небольшое расширение контракта. Это экспертная оценка, не срок и не обещание результата.

| № | Решение и действие | Приоритет / основание | Проверяемое условие |
|---|---|---|---|
| 1 | **Добавить быстрый доступ к работе, требующей внимания:** «На проверке», «Заблокировано», «Без исполнителя». Это представления той же доски; у каждого явный критерий и счётчик. | P0, малая; наблюдение статичных счётчиков + гипотеза об ускорении выбора | Один выбор показывает нужные задачи, повторный/«Все» возвращает область. «Без исполнителя» не называть «готово к работе»: зависимости и claim имеют другой смысл. |
| 2 | **Доработать фильтры:** одинаковая семантика в доске и списке; видимые активные значения, понятная область поиска, число «показано из всего», сброс рядом. | P0, малая; подтверждённая непоследовательность + [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/filtering-projects) | Переключение вида сохраняет множество результатов. Нулевой результат не выглядит пустым проектом. Фильтр подпроекта явно включает вложенные. |
| 3 | **Доработать проверку результата:** в подробностях рядом с критериями вывести последнее evidence с автором и датой, затем изменения/commit и полную историю. | P0, малая; исследования проверяемости и наблюдение потока notes | Человек находит проверку без просмотра всех записей. Надпись «Проверка приложена» не превращается в «Проверено системой». Старое evidence не объявляется проверкой нового commit. |
| 4 | **Убрать технический шум из основного просмотра:** версии записей перенести в технические подробности; глобальный каталог агентов убрать из роли «участников проекта»; сократить вторичные подписи. | P0, малая; наблюдение интерфейса | Номер релиза и revision записи невозможно спутать. Ни один визуальный индикатор не намекает на запуск или связь без соответствующего факта. |
| 5 | **Доработать визуальную иерархию и плотность:** компактная шапка, одно главное действие, читаемый заголовок карточки, вторичная метаинформация, спокойные границы и согласованные состояния фокуса/выбора. | P0, малая; экспертная UX-гипотеза | На обычном webview видно больше полезных задач, без уменьшения основного текста и кликабельных целей. Семантика цветов стабильна; статус читается текстом. |
| 6 | **Доработать первый запуск:** путь «проект → первая задача → подключение → реальный запрос» с проверяемым результатом каждого шага. | P1, средняя; HAX + гипотеза новичка | Пользователь объясняет различие «исполнитель добавлен», «конфиг подготовлен», «последний запрос получен». Ошибка 401 даёт понятный следующий шаг, без выдачи offline/demo за сохранённую работу. |
| 7 | **Упростить форму без потери смысла:** начать с результата, rationale и критериев; редкие поля сгруппировать. Подпроект необязателен; активный контекст можно предложить как редактируемое значение. | P1, малая; наблюдение формы + гипотеза снижения нагрузки | Можно создать содержательную задачу без предварительного построения дерева. Обязательные данные не спрятаны, ошибки ведут к полям, черновик сохраняется. Reason остаётся явным, а не молча генерируется системой. |
| 8 | **Доработать историю:** быстрые режимы «Решения», «Проверки», «Изменения»; краткий результат события, раскрываемое «было → стало», точное время. | P1, малая/средняя; существующая модель notes/events | После нескольких десятков записей пользователь находит причину выбранного решения. Фильтрация не удаляет audit и не меняет экспорт; поиск по загруженному фрагменту обозначает свою границу. |
| 9 | **Добавить восстановление рабочего контекста:** сохранять фильтры/вид для проекта и ссылку на конкретную задачу, если текущая оболочка это поддерживает. | P1, средняя; [сохраняемые представления GitHub](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/filtering-projects) + гипотеза повторной работы | После возврата открывается ожидаемая область. Удалённая/недоступная задача даёт явное состояние; URL не содержит credentials. Начать с текущего вида, без универсального конструктора запросов. |
| 10 | **Доработать доступность и длинные данные:** keyboard, 320/390 px, zoom, видимый фокус, длинные названия/пути, error recovery; сохранить действие без drag. | P0, малая/средняя; W3C, проверяется отдельно | Все основные сценарии доступны с клавиатуры и указателем без перетаскивания. Текст и фокус не перекрыты; нет горизонтального скролла всей страницы при 320 CSS px. |
| 11 | **Добавить архив при подтверждённом накоплении:** завершённые проекты/задачи уходят из ежедневного вида и восстанавливаются, сохраняя ID и историю. | P2, средняя; гипотеза длительного использования | Не удаляются notes, зависимости, evidence и экспорт. Сначала проверить реальный объём и достаточность фильтра завершённых; не добавлять bulk delete. |
| 12 | **Доработать чтение состояния знаний и интеграций:** дата/снимок объяснения, проверенное назначение публикации, понятные pending/conflict/unknown и путь восстановления. | P1, средняя; уже существующий контракт проекта | Пользователь понимает, что опубликовано, где и для какого снимка, и отличает ожидающую отправку от успеха. Выключение сохраняет данные, uncertain create не повторяется вслепую. |

Пункты 1–5 и 10 образуют минимальный связный пакет для текущей доработки UI. Таблица фиксирует рекомендации, сформированные перед изменениями; их текущий статус указан ниже. Пункт 3 использует существующие notes; полноценный reviewer verdict с reviewed commit/version требует отдельного общего API-контракта для UI и MCP.

### Сопоставление с изменениями 18.10.2026

Повторное чтение текущих `App.tsx` и `KanbanBoard.tsx` после доработки подтвердило наличие быстрых выборок, общего статусного фильтра доски/списка, видимых значений активных фильтров, счётчика найденных задач и отдельного состояния первого запуска пустой доски. Технические revision-номера убраны из обзорных карточек; общий каталог агентов больше не показан как участники каждого проекта. Добавлен блок последнего evidence с автором, временем и явным ограничением: DashAI сам проверки не выполняет. Это реализованная основа пунктов 1–4, а не оставшиеся предложения построить её заново.

Для пунктов 6–7 появились отдельные улучшения: подсказка первого действия, наследование выбранного подпроекта и защита несохранённых форм. Полный onboarding с подтверждённым MCP-запросом и дальнейшее сокращение формы ещё требуют отдельной проверки и решения. История получила загрузку последних событий и более ранних страниц; предлагаемые режимы по смыслу записей из пункта 8 остаются backlog. Архив и дальнейшее улучшение интеграций из пунктов 11–12 не объявляются реализованными этим аудитом.

В следующей итерации 18.10 реализована минимальная версия пункта 9: восстановление текущего проекта, вкладки, фильтров, доски/списка и открытой карточки; прямые локальные ссылки на задачи. Именованные наборы представлений и сложный язык запросов не добавлялись. Browser regression проверяет восстановление, явную ссылку поверх сохранённого состояния, Back/Forward с черновиком и ошибки storage. [Отчёт реализации](../reviews/workspace-navigation-review.md). Это инженерное подтверждение поведения, а не измеренный эффект для пользователей.

Обновление дизайна и accessibility из пунктов 5 и 10 проверяется на уровне браузерных сценариев отдельным исполнителем. Статическое наличие кода не доказывает прохождение сценария, WCAG-соответствие или пользовательский эффект. Входной аудит выше намеренно сохранён как состояние до изменений. Повторная сверка трёх ключевых первичных страниц — SO 2026 AI, SO 2026 Knowledge и JetBrains/Lund review — подтвердила приведённые цифры и размер выборок; изменения выводов не потребовались.

## Какие механизмы аналогов стоит перенести

[Linear Inbox](https://linear.app/docs/inbox) отделяет уведомления, требующие внимания, от прочих обновлений, позволяет искать и управлять отображением. Для DashAI это основание проверить короткую очередь внимания. Полный notification center с подписками, напоминаниями, email и push не требуется для первой итерации.

[GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/filtering-projects) поддерживает комбинацию фильтров, сохранённые представления и запросы по незаполненным полям. Переносим предсказуемую семантику и быстрые рабочие выборки. Синтаксис сложных запросов и универсальная система views имеют смысл только после подтверждения, что обычных контролов недостаточно.

Это product references. Наличие механизма у популярного инструмента не доказывает спрос на его копию в DashAI.

## Что убрать или пока не строить

- Убрать из основной поверхности дублирующую статистику, технические revision-номера и декоративные признаки «активности». Реальные сведения остаются в подробностях и истории.
- Не удалять доступное действие перемещения вместе с визуальным шумом. При его уплотнении сохранить понятный путь для клавиатуры и одного указателя без drag.
- Не строить встроенный runtime моделей, chat/terminal orchestrator, собственный diff-IDE, маркетплейс исполняемых плагинов, универсальный workflow canvas или RAG. Сейчас нет подтверждённого пользовательского сценария, оправдывающего эту поверхность и инфраструктуру.
- Не добавлять оценки «эффективности AI», confidence 98%, часы экономии или рейтинги агентов из количества событий. У продукта нет источника, позволяющего подтвердить эти числа.
- Не вводить ещё один обязательный контейнер поверх проекта, подпроекта и задачи; тип работы, статус и принадлежность остаются разными полями.
- Не превращать каждую запись агента в toast/push. Сначала сделать важное легко находимым; уведомления проверять отдельно на пользе и частоте прерываний.
- Не ставить обязательный tour перед первым результатом и не заполнять рабочую доску непомеченными примерами. Подсказки должны находиться у соответствующего действия.
- Не сокращать audit, validation, data safety, разрешение conflicts и accessibility ради компактной формы или меньшего числа строк.

## Требования к проверке дизайна

Визуальное направление — рабочая доска с ясными уровнями: навигация → цель проекта → управление выборкой → задачи. Контент задачи должен сильнее привлекать внимание, чем рамка, счётчик или вторичная кнопка. Тёмная тема сама по себе не делает интерфейс удобным; важны измеримый контраст, плотность, предсказуемость и состояние ошибок.

Нормативная основа:

- [WCAG 2.2 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html): проверить 320 CSS px; двумерная доска не оправдывает обрезанные формы и текст. Список должен давать доступ к тем же данным.
- [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): минимум 24×24 CSS px с предусмотренными стандартом исключениями; продуктовая цель для частых touch-действий — около 44 px.
- [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html): sticky-шапка и drawer не должны полностью скрывать сфокусированный элемент.
- [Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html): кроме keyboard, требуется альтернатива одному указателю без drag, если не действует исключение.
- [GOV.UK Error summary](https://design-system.service.gov.uk/components/error-summary/): ошибка связана с полем, summary и inline-сообщение согласованы; пользователь понимает способ исправления.

Эта подборка не является заявлением полного соответствия WCAG. Нужны ручные проверки клавиатуры и screen reader, проверка контраста, адаптивности и реальных задач. Автотест и скриншот дополняют, но не заменяют их.

## Как проверить потребности с людьми

### Раунд 1: выявить рабочие проблемы

Набрать 6–8 участников: опытные пользователи двух или более coding agents, пользователи одного помощника и новички MCP; включить людей, работающих в узком IDE-webview, с увеличением или клавиатурой. Это качественное исследование, не репрезентативный опрос рынка. Не объединять все результаты в один «средний портрет».

Провести 35–45-минутные сессии на очищенных примерах или данных, которые участник согласен показать. Просить рассказать о последнем реальном случае: «Когда вы в последний раз не понимали, завершил ли агент задачу?», «Как проверили?», «Где искали прошлую причину решения?», «Что пришлось переносить вручную?». Не начинать с «Нравится ли вам очередь внимания?» — это подсказывает решение.

Фиксировать действие, препятствие, обходной путь и последствия. Отделять повторяющуюся боль от пожелания новой функции. Не собирать токены, приватный код или полный экран без согласия.

### Раунд 2: сравнить текущий и улучшенный поток

Провести два коротких раунда по 5–6 участникам, исправляя серьёзные проблемы между раундами. Участникам сравнения давать эквивалентные, но разные наборы задач и менять порядок версий, чтобы снизить эффект обучения. Маленькая выборка помогает находить проблемы; статистически значимый рост конверсии по ней не заявлять.

| Сценарий | Что наблюдаем | Предварительный критерий успеха |
|---|---|---|
| После паузы найти работу, ожидающую проверки, и объяснить следующий шаг | Первый выбор, время поиска, лишние переходы | Не менее 4 из 5 выполняют без подсказки; объясняют причину выбора |
| Найти задачу по тексту/ID и подпроекту; сменить доску на список | Сохранение области, понимание активных фильтров | Участник предсказывает, какие задачи останутся; нет ошибочного вывода о потере данных |
| Проверить задачу с длинной историей, старым evidence и новой правкой | Видит источник, время, ограничения проверки | Никто не принимает старое evidence за автоматически подтверждённый новый результат |
| Создать задачу без подпроекта и сохранить при ошибке сети | Полнота контекста, ошибки формы, сохранность черновика | Нет потери введённого текста; понятен повтор и отсутствие дубля |
| Подготовить конфиг, затем выполнить настоящий MCP-запрос | Различение конфигурации и контакта | Участник правильно называет оба состояния; реальная задача видна после reload |
| Пройти поиск → подробности → изменение статуса клавиатурой и на 320/390 px | Фокус, горизонтальный overflow, доступность действий | Сценарий завершён без мыши/drag; фокус и кнопки не скрыты |

Порог 4 из 5 — предварительное правило принятия решения для маленького раунда, а не отраслевой норматив. Любая потеря данных, ложный статус подключения или недоступное основное действие блокируют выпуск независимо от среднего времени.

### Раунд 3: проверка ежедневного использования

После успешных сессий — двухнедельный пилот с 8–12 добровольными пользователями. Вести короткий дневник: зачем открыли DashAI, нашли ли ответ, что пришлось искать снаружи. Через неделю проверить, действительно ли нужны saved views, архив и уведомления. Этот пилот не проводится автоматически и не означает согласие пользователей на телеметрию.

## Метрики и правила решений

| Метрика | Как измерять | Что не следует заключать |
|---|---|---|
| Время до правильного следующего шага | От открытия проекта до выбора задачи с верным объяснением причины; сравнивать медиану и диапазон на эквивалентных заданиях | Быстрый клик сам по себе не означает правильное решение |
| Успешность поиска/фильтрации | Доля задач сценария, выполненных без помощи; отдельно новички и опытные | Общая частота использования фильтра не доказывает полезность |
| Понимание evidence | Участник называет, кто, что и когда проверил, и что остаётся неизвестным | Наличие evidence note не подтверждает качество кода |
| Стоимость повторной работы | Сколько действий требуется восстановить рабочий вид/найти прошлое решение | Длительная сессия не обязательно означает вовлечённость |
| Первое подтверждённое подключение | Время и доля успешных реальных запросов после setup, отдельно ошибки 401 и недоступный API | Сгенерированный конфиг не считается активацией |
| Ошибки и восстановление | Потерянные черновики, unintended status changes, неверно понятые состояния, обращения за помощью | Низкое число ошибок без попыток использования не означает хороший UX |
| Время ручной проверки | Время чтения результата и артефактов, возвраты на доработку; учитывать сложность задачи | Количество done или tool calls не является продуктивностью |

Сначала получить baseline; численное обещание «ускорить на 30%» до измерения не делать. Для сравнительного теста можно заранее установить продуктовую цель снижения медианного времени поиска при отсутствии ухудшения правильности, затем указать фактические значения и размер выборки.

Для локального продукта достаточно добровольных сессий и обезличенного протокола. Автоматический сбор telemetry и отправка названий задач/содержимого заметок не нужны для первой проверки. Если позднее появится инструментирование, оно должно быть явно включаемым и собирать только необходимое для заранее выбранной метрики.

## Решение на текущую итерацию

Сначала улучшить ежедневный цикл «найти → понять → проверить → продолжить» на существующей модели. Проверять UI на настоящих формах, ошибках, длинных данных и доступности; отдельно проверить domain-инварианты соответствующими тестами. Зафиксировать, что изменено и что реально проверено. После пользовательских сессий пересмотреть P1/P2: список рекомендаций не является обязательством построить все функции.
