# UX/UI исследование: рабочая доска человека и coding agents

Дата проверки первичных источников: 3 октября 2026 года. Исследование выполнено до реализации интерфейса. Ниже — 26 прочитанных первичных страниц: стандарт, авторские design systems, документация продуктов и исследования их авторов. Публикация и PDF одной статьи считаются одним источником; неработающие адреса не включены. Это экспертный анализ, а не проведённое пользовательское исследование. Размеры, палитра и продуктовые решения — собственная спецификация на основании источников.

## 1. Что человек должен понять за несколько секунд

Доска отвечает на четыре разных вопроса: какой результат нужен проекту; какие части работы выделены; кто сейчас делает конкретную задачу; чем подтверждаются изменения и почему их сделали. Первая информация принадлежит проекту, вторая — секции, третья — карточке, четвёртая — подробностям и журналу. Их нельзя сводить в одну бесконечную ленту событий.

Пользовательский сценарий: человек создаёт проект «Редизайн кабинета» и секцию «Авторизация»; агент создаёт задачу «Добавить восстановление пароля» с объяснением и критериями готовности; агент отмечает начало работы; добавляет результат, файл/commit и проверку; человек открывает задачу и принимает результат либо возвращает на доработку с причиной. Основной экран показывает продвижение, детали сохраняют аргументацию.

В Human-AI Guidelines важны объяснение возможностей, возможность исправления и доступное объяснение действий системы. Для нашего продукта это означает явную идентичность автора, понятную историю переходов и доступную ручную коррекцию. Объяснение агента является его записанным обоснованием; интерфейс не выдаёт его за доказательство истинности. [Microsoft Research, CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)

## 2. Информационная архитектура

```text
Рабочее пространство
└── Проект: цель, репозиторий/путь, краткое описание
    ├── Секция: крупная задача / направление / эпик
    │   ├── Задача: действие + результат + исполнитель + состояние
    │   └── Задача
    └── Секция

Задача → описание, зачем, критерии, артефакты, события
Событие → автор, действие, причина, до/после, время, источник
```

Секция — отдельная часть проектной доски, а не статус. Статус «В работе» пересекает все секции. У задачи ровно один проект и одна секция; поиск может показывать их вместе, сохраняя хлебные крошки. В первоначальной версии глубина ограничена этими тремя уровнями: бесконечное дерево ухудшает обозримость. Если нужны мелкие пункты, подходят критерии готовности, а не ещё один уровень досок.

Декомпозиция соответствует моделям parent/sub-issues в Linear и GitHub. Однако секция здесь является направлением работы с собственной целью, а задачи — самостоятельными единицами выполнения. Нет автоматического закрытия всей секции после изменения одной карточки. [Linear: Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues), [GitHub: Adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)

## 3. Основной экран

### Desktop

Левая панель около 232–248 px: знак продукта, имя рабочего пространства, «Обзор», «Проекты», «История», «Коннекторы», список проектов и кнопка создания. Внизу — статус локального сервиса и профиль. Выбранный проект заметен по фону и текстовой метке, а не одному цветному кружку.

В центре верхняя компактная полоса: хлебные крошки, поиск, индикатор актуальности данных, действия. Далее название проекта, однострочная цель, ссылка на репозиторий и кнопки «Новая секция», «Новая задача». Небольшие счётчики выводятся только из настоящих данных: всего задач, в работе, ждут проверки, заблокированы. Не нужны крупные графики производительности или декоративные проценты «эффективности ИИ».

Вкладки проекта: «Доска», «История», при необходимости «Обзор». Внутри доски компактная строка фильтров: секция, исполнитель, статус, приоритет; активные значения видны, «Сбросить» появляется при фильтрации. Поиск явно ограничен проектом и находит ID, заголовок, описание и обоснование. Глобальный поиск из оболочки отдельно показывает проект каждого результата.

Доска по умолчанию использует четыре колонки: «Очередь», «В работе», «Проверка», «Готово». Каждая секция образует раскрываемую горизонтальную полосу с названием, целью и количеством задач. Если секций очень много, фильтр одной секции превращает полосу в обычную доску. Внутри колонки отображается состояние; в заголовке секции — принадлежность. Такие горизонтальные группы подтверждены в документации Linear и GitHub. [Linear: Board layout](https://linear.app/docs/board-layout), [GitHub: Customizing board layout](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-board-layout)

«Заблокирована» — отдельное явное состояние или хорошо различимая метка с причиной и зависимой задачей. В любом варианте её количество и фильтр должны присутствовать. Не помещать блокировку только внутрь текста описания.

### Карточка задачи

Карточка содержит стабильный ID, приоритет, заголовок до трёх строк, короткую метку секции при необходимости, исполнителя с названием клиента, количество событий/артефактов и время последнего изменения. Излишние теги скрываются в подробностях. Тип клиента — Codex, Claude Code или человек — виден текстом; цвет дополняет его. Заголовок и действие открытия — настоящий button/link, а не div с click handler.

Карточка открывает подробности. Перемещение между статусами доступно через select или меню внутри подробностей, независимо от drag-and-drop. Создание из конкретной секции и колонки заранее устанавливает их значения. Эта локальная кнопка вторичная; единственная заметная primary-кнопка в шапке — «Новая задача».

Вместо полного описания на карточке — постепенное раскрытие. Детали доступны в боковой панели; проектная доска остаётся опорой для ориентирования. [Carbon: Data table](https://carbondesignsystem.com/components/data-table/usage/)

## 4. Подробности и история решения

На широком экране подробности занимают правую панель 420–480 px, на узком — отдельное полноэкранное представление. Порядок блоков: ID и заголовок; состояние, исполнитель, приоритет; «Что делаем»; «Зачем»; «Критерии готовности»; «Результат и проверки»; «История».

Событие читается как предложение: «Codex перевёл AD-014 в Проверку · 14:32». Под ним причина: «Добавлена проверка отменённой сессии; unit tests прошли». Изменения полей раскрываются как «Было → Стало». Артефакты — отдельные ссылки на путь/commit/test output. Для длинных технических данных используется раскрытие «Показать детали», сохраняющее видимость человеческого объяснения.

Обязательны различия между автором операции и исполнителем задачи. «Создано Claude Code» не означает «назначено Claude Code». Поле причины не заменяет описание: описание — предполагаемая работа, причина события — мотивация конкретного изменения. «Проверки не приложены» отличается от «Проверки прошли».

Журнал проекта поддерживает поиск, фильтр автора, типа события и задачи. По умолчанию новые события сверху, группировка по дате. В задаче полезен последовательный ход событий. События сохраняют серверное время; UI показывает локальное время пользователя и точную дату в доступных подробностях. Не относить старую запись только к «вчера», когда пользователь читает архив.

Человек может вернуть карточку на доработку с причиной. Для чтения журнала никаких подтверждений не требуется. Коннектор не должен показывать выдуманную «уверенность 98%»: PAIR предупреждает о трудностях интерпретации численной уверенности. Понятнее показать приложенное доказательство, источник события и наличие человеческой проверки. [Google PAIR: Explainability + Trust](https://pair.withgoogle.com/guidebook-v2/chapter/explainability-trust/)

## 5. Создание и изменение

Форма проекта: название, цель, путь/URL репозитория. Форма секции: название, цель, проект. Форма задачи: название, секция, описание, «Зачем это нужно», критерии, исполнитель, приоритет. Первое поле получает фокус. У каждого поля постоянная подпись; placeholder — пример, не замена label. Нажатие Enter в textarea добавляет строку, не отправляет форму. [GOV.UK: Textarea](https://design-system.service.gov.uk/components/textarea/)

Неуспешное сохранение не очищает введённые данные. Поле с ошибкой получает сообщение рядом; наверху формы — короткий список со ссылками на ошибочные поля. Сообщения одинаковы в обоих местах. Например: «Укажите название задачи» и «Выберите секцию», а не «Invalid payload». [GOV.UK: Error summary](https://design-system.service.gov.uk/components/error-summary/)

При сохранении UI показывает pending-state и предотвращает повторную отправку. После подтверждения сервера появляется новая карточка, число в колонке обновляется, а короткое status-сообщение сообщает успех. При конфликте изменения: «Задачу уже обновил Claude Code. Обновите данные и повторите изменение», с сохранённым черновиком. Конкретный механизм concurrency — отдельная архитектурная задача.

Баннеры используются для долговременных общих проблем; локальная ошибка находится возле своего действия. Toast подходит для короткого подтверждения, но не является единственным местом ошибки. [Carbon: Notification](https://carbondesignsystem.com/components/notification/usage/), [GOV.UK: Notification banner](https://design-system.service.gov.uk/components/notification-banner/)

## 6. Коннекторы: понятный контракт для человека

Экран «Коннекторы» показывает отдельно Codex, Claude Code и Ponytail: роль интеграции, способ подключения, состояние, последнюю реальную активность, endpoint и готовый блок конфигурации с кнопкой копирования. У каждого шага есть результат, который можно проверить. Команды показываются как код только на этом техническом экране.

Состояния: «Настроен» значит конфигурация подготовлена; «Подключён» значит проверенное взаимодействие; «Нет активной сессии» значит нет текущего heartbeat/достоверного признака активности; «Ошибка» содержит диагностируемую причину. Задача «В работе» не доказывает, что агент сейчас подключён. Пользователь должен отличать подготовленную интеграцию от работающего клиента.

Агенты используют тот же смысл полей, что человек: create project → create section → create task → record change with reason → attach evidence → request review. Человек может видеть и исправлять их результаты в UI. Это продуктовая адаптация принципа баланса автоматизации и контроля. [Google PAIR: Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)

Ponytail следует отражать в интерфейсе ровно в той роли, в которой он реально использован проектом. Наличие vendored repository само по себе не даёт оснований писать «Ponytail подключён»; конкретная интеграция проверяется отдельно.

## 7. Визуальная система

Направление: спокойная профессиональная диспетчерская. Рабочая поверхность приоритетнее иллюстрации. Тёмный фон с несколькими ступенями светлоты даёт разделение sidebar, рабочей области, карточек и панелей. Используются семантические design tokens, а не случайные hex значения в каждом компоненте. Идея последовательного осветления уровней опирается на Carbon. [Carbon: Color](https://carbondesignsystem.com/elements/color/overview/)

| Токен | Предложение | Назначение |
| --- | --- | --- |
| background | `#0B0F14` | Общая поверхность |
| surface | `#111821` | Sidebar и колонка |
| surface-raised | `#17212D` | Карточки, диалоги |
| border | `#2A3645` | Спокойное разделение; не самостоятельная гарантия контраста |
| text | `#F0F3F7` | Основной текст |
| text-secondary | `#A4AFBF` | Подписи |
| accent | `#B4F4A5` | Primary action, выбранное действие |
| codex | `#7DD3E8` | Дополнительный идентификатор Codex |
| claude | `#C4B0FA` | Дополнительный идентификатор Claude Code |
| warning | `#F0C675` | Блокировка, требуемое внимание |
| danger | `#FF9B9B` | Ошибка |

Палитра требует расчёта контраста на реальных сочетаниях. Слишком тонкая граница может быть декоративной, но состояние input, focus и необходимые иконки должны иметь достаточный контраст. Для selected/disabled/hover предусмотрены отдельные токены. Цвет клиента не становится цветом статуса; оба смысла нельзя кодировать одной и той же точкой.

Typography: системный sans с кириллицей или локально поставляемый шрифт; 14 px основной рабочий текст, 12–13 px метаданные, 22–28 px название проекта. Межстрочный интервал 1.4–1.6; monospace для ID, пути и команд. Сетка отступов 4/8 px, padding карточки 14–16 px, gap 12–16 px, радиусы 8–12 px. Умеренная плотность допускает чтение нескольких карточек сразу. Избегать капслока в длинных русских подписях.

Движение 120–180 ms только для перехода состояния; отсутствуют мигающие «живые» метрики. В `prefers-reduced-motion` анимации отключены. Собственная визуальная индивидуальность создаётся компактным знаком, аккуратной типографикой, спокойным mint-акцентом и выразительными рабочими состояниями. Принцип focus-first описан в Fluent. [Fluent 2: Design principles](https://fluent2.microsoft.design/design-principles)

## 8. Accessibility и responsive

Цель — WCAG 2.2 AA по проверенным критериям; соответствие не заявляется до аудита. Основной текст: 4.5:1, крупный: 3:1; значимые контуры и графика: 3:1. В документе `lang="ru"`. Native button/input/select предпочтительнее самописного ARIA. Каждая icon button имеет доступное имя, а декоративная иконка скрыта от screen reader. [W3C: WCAG Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/)

Минимум 24×24 CSS px для цели указателя с предусмотренными стандартом исключениями; практическая цель продукта — 36–40 px на desktop и 44 px на touch. Выбранный статус обозначается текстом. Все необходимые действия выполняются клавиатурой. Перетаскивание дополняется обычным select/menu: клавиатурной альтернативы самой по себе недостаточно для людей с touch-устройствами, которым нужен способ без drag. [W3C: Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [W3C: Dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

Диалог: role/label, фокус внутри при открытии, замкнутый Tab, Escape, видимая кнопка закрытия, возврат фокуса инициатору. Нельзя ставить `aria-modal=true` на панель, оставляя фон интерактивным. Настоящая немодальная панель имеет иной контракт. [W3C APG: Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

Вкладки либо реализуют полноценный APG keyboard pattern, либо оформляются обычными ссылками/кнопками навигации без ложного `role=tab`. Поиск с простым input не требует combobox. Если есть выпадающие результаты, keyboard interaction и active descendant должны соответствовать выбранному combobox pattern. Раскрытие секции — button с `aria-expanded` и при необходимости `aria-controls`. [W3C APG: Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), [W3C APG: Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [W3C APG: Disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)

Обновления данных не отнимают фокус. После создания/сохранения короткая область `role=status` сообщает результат. Не объявлять screen reader каждое обновление общей ленты; результат собственного действия и критическая ошибка важнее фонового трафика. Sticky header и drawer не скрывают focused control. [W3C: Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [W3C: Focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

На 1280+ px доступны sidebar и все четыре колонки. На 768–1279 px sidebar сворачивается, подробности могут стать modal drawer. Ниже 768 px — компактная шапка, меню проектов, статусные вкладки/stacked sections или список; формы и история занимают полную ширину. 320 CSS px — отдельная проверка reflow; горизонтальный scroll у текста недопустим. Если сохраняется двумерная доска, есть удобный доступный список тех же задач. [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 9. Пустые и пограничные состояния

Новый workspace: «Создайте первый проект» и одно действие. Проект без секций: «Разделите проект на направления» и «Новая секция». Пустая секция: краткое «Пока нет задач» и локальная secondary-кнопка. Отфильтрованная пустота: «Ничего не найдено» с «Сбросить фильтры», а не предложение создать ещё один проект. Ошибка загрузки: конкретная причина и повторная загрузка. Демоданные помечаются как пример, если используются. [Carbon: Empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/)

Под длинными данными понимаются: русские заголовки 120+ символов, Windows paths, причины на несколько абзацев, десятки событий, много секций, отсутствие исполнителя. Текст переносится; путь имеет возможность копирования; full title доступен в подробностях. Поиск указывается в ожидаемом месте рядом с данными, а не прячется в onboarding. [Carbon: Search](https://carbondesignsystem.com/components/search/usage/)

## 10. План отдельной UX-критики после реализации

Критик не оценивает «красиво» по исходному CSS. Он открывает работающий UI и проходит реальные сценарии. Каждая проблема фиксируется с шагами, фактическим результатом, ожидаемым результатом и серьёзностью. После исправления проверяется тот же сценарий.

| Проверка | Критерий приёмки |
| --- | --- |
| Создать проект → секцию → задачу | Новые данные видны после reload; принадлежность очевидна |
| Перевести задачу в работу и на проверку | Карточка перемещается, событие содержит автора и причину |
| Прочитать историю | Можно восстановить что, почему, когда, кем и с каким доказательством |
| Найти задачу и сбросить фильтр | Область поиска понятна; пустой результат объяснён |
| Подключить клиент | Конфигурация копируется; реальный статус не смешан с setup |
| Работа с клавиатуры | Нет traps вне modal; видимый focus; Escape и возврат focus работают |
| 390 px и 320 px | Доступны все действия, заголовки читаемы, формы не обрезаны |
| Long content | Причины, путь и название не ломают layout |
| Ошибка сети/сохранения | Данные формы сохраняются; ошибка понятна и связана с действием |
| Пустой workspace | Есть конкретный следующий шаг, нет fake активности |

Это критерии проекта; факт прохождения появится в отдельном отчёте критика.
