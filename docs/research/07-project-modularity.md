# Модульность DashAI: рынок, потребности и решение

Проверено 17 октября 2026. Это целевое продолжение [исследования 38 продуктов](01-products.md), а не повторный подсчёт того же рынка. Пользователь уточнил ориентир: **Langfuse**. Сравнение ниже основано на первичных документах и одном публичном запросе пользователя Langfuse. Оно не заменяет интервью или измерение спроса; выводы для DashAI явно отделены от механизмов аналогов.

## Что именно нужно пользователю

Исходные требования этой сессии — наиболее прямое свидетельство потребности: большой репозиторий должен оставаться обозримым; архитектурные знания не должны вручную копироваться в Confluence/Jira; работа не должна зависеть от двух названий моделей; ненужные возможности можно убрать из конкретного проекта. Это проектный рабочий инструмент человека и внешних агентов, а не среда исполнения LLM.

## Сценарии и приоритеты

1. **Разобраться в большом проекте.** Поиск по пути и смыслу, свёрнутое дерево, независимое чтение описания и раскрытие пути выбранного файла. Проверка — ограниченное число DOM-строк при тысячах файлов, клавиатура и мобильная ширина.
2. **Сохранить архитектурное знание один раз.** Включённые описания и схемы отправляются в заранее проверенное назначение. Проверка — Cloud/DC адаптеры, запрет записи вне корня, очередь, конфликт внешней версии, повтор после сетевой ошибки без слепого создания.
3. **Подключить ещё одного исполнителя.** Свободное имя отдельно от формата клиента. Проверка — реальная MCP-сессия custom identity, авторство и claim, конфиги известных клиентов, отсутствие ложного статуса подключения.
4. **Убрать шум в небольшом проекте.** Существующие вкладки можно выключить и вернуть без потери данных. Доска и история остаются основой; каталог всегда доступен.
5. **Повторять полезную структуру знаний.** ADR, риски и runbook — готовые редактируемые документные модули. Пользователь создаёт собственный шаблон, добавляет в разные проекты, заполняет независимый текст; агент читает и редактирует через тот же API.

Первые три сценария прямо запрошены пользователем. Последние два — предлагаемое минимальное воплощение его запроса на модульность, подкреплённое механизмами аналогов. Это не результат количественного UX-исследования.

## Принятое решение 1.6

- Каталог встроенных функциональных модулей: карта, архитектура, документация, Confluence/Jira. Для существующих проектов первые три включены; внешняя отправка выключена по умолчанию.
- Документные модули ADR, рисков и эксплуатации, плюс собственные повторно используемые шаблоны. Это реальные документы с сохранением, версией, авторством, экспортом и общим MCP-контрактом.
- Добавление/отключение — атомарное изменение конфигурации и audit. Данные отключённого модуля остаются в SQLite. Внешняя отправка запрещена, когда её модуль отключён.
- Переключатели обозначают доступность поверхности, а не права доступа к данным. Локальная модель доверия одного пользователя ОС сохраняется.
- Новая встроенная возможность добавляется в явный каталог и маршрут UI, использует общий Store/API/MCP и получает проверку. Пользовательские шаблоны не исполняют код и не добавляют зависимости.

## Что исследование не обосновало

Не найдена необходимость добавлять запуск моделей, отдельные хранилища каждого модуля, удалённый plugin runtime, собственный инструмент evaluation/трейсинга или универсальный workflow-конструктор. Эти направления требуют самостоятельного пользовательского сценария, схемы данных и проверки. Запрос «как Langfuse» сам по себе их не предполагает.

## Практические ограничения интеграций

Ссылка определяет назначение, но не даёт права записи. Личные подключения пользователя хранятся только на его компьютере, отдельно для каждого проекта. Проверяются реальные ответы выбранного сервиса; тесты с сетевыми моками не выдаются за проверку tenant пользователя. Для распространяемого Cloud OAuth потребуется единое зарегистрированное приложение и сервер авторизации; их нет в текущем проекте. [Atlassian описывает 3LO и отличие от личного REST-доступа](https://developer.atlassian.com/cloud/confluence/oauth-2-3lo-apps/). Data Center использует свой HTTPS endpoint и PAT; подробный контракт — [интеграции](../integrations.md).
