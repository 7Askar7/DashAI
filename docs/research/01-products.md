# Исследование аналогов: доска проектов для человека, Codex и Claude Code

Дата проверки: **3 октября 2026 года**. Рассмотрены **38 самостоятельных проектов и продуктов**, из них 17 прямых аналогов управления работой, 4 инструмента совместной работы с coding agents, 5 платформ агентов, 4 системы наблюдаемости, 7 движков автоматизации и Ponytail как обязательный инструмент разработки. Разные страницы одного продукта не увеличивают счетчик.

## Метод и границы доказательств

Источники — официальная документация, сайты разработчиков и README репозиториев авторов. Страницы открывались и читались; у GitHub проектов дополнительно изучались основные разделы README, включая raw-версию, когда навигация GitHub скрывала полезный текст. Каталоги, SEO-сравнения и рекламные списки не использовались как доказательства.

В таблице «Проверенный механизм» означает механизм, сверенный с указанным первичным документом, **а не функцию, независимо протестированную нами в установленном продукте**. «Компромисс для нашего сценария» — аналитический вывод о применимости механизма к запросу пользователя, **а не утверждение, что продукт не имеет других функций или интеграций**. Отсутствие функции в прочитанном документе не считается доказательством отсутствия в продукте. Исследование не заменяет нагрузочное сравнение установленных экземпляров, проверку платных тарифов и пользовательские интервью.

Запрос пользователя состоит из четырех связанных потребностей: отдельная доска каждого проекта; отдельный раздел большой работы; небольшие задачи внутри разделов; восстанавливаемая история действий и их причин, доступная человеку и агентам через коннектор.

Генерация typed UI полезна без исполнения произвольных скриптов. | Явные схемы входов; server не исполняет произвольную команду из MCP. Секреты коннектора не включать в историю. |
| 34 | [Trigger.dev — Official README](https://raw.githubusercontent.com/triggerdotdev/trigger.dev/main/README.md) | Durable tasks, retries, queues, idempotency, pause for approval, realtime run subscriptions и tracing. | Retry сетевой операции создания задачи может создать дубль, если API не отличает повтор намерения от новой команды. | Request/idempotency ID для мутаций и версия сущности. Human review выделить в статус и отдельное событие. |
| 35 | [Inngest — Official README](https://raw.githubusercontent.com/inngest/inngest/main/README.md) | Events, durable steps, concurrency/throttling; runner хранит поступившие события для history/replay, state store хранит outputs/errors. | Execution history восстанавливает шаги, но не должен использоваться для повторного выполнения действий проекта без политики replay. | History только читается; повторное изменение — новая операция с причиной. Конкуренцию контролировать атомарно. |
| 36 | [Activepieces — Official README](https://raw.githubusercontent.com/activepieces/activepieces/main/README.md) | Type-safe TypeScript pieces становятся MCP servers; flows версионируются; есть retries, human approval и human input interfaces. | Большое число интеграций создает большое пространство инструментов и разрешений. | Небольшой domain-specific MCP; tools говорят языком проекта/раздела/задачи и сообщают понятные ошибки. |
| 37 | [n8n — Official README](https://raw.githubusercontent.com/n8n-io/n8n/master/README.md) | Visual canvas сочетается с custom code, human approvals, observability, audit trails и множеством интеграций; self-host/cloud. | Универсальные workflow platforms дают широкие права и много настроек; коннектор для coding agents нуждается в узком контракте. | Отдельный общий service layer для UI и MCP. Внешние интеграции добавлять после проверки основного workflow. |

## Сравнение классов решений

| Класс | Главный объект | Что помогает человеку | Что помогает агенту | Что переносим |
|---|---|---|---|---|
| Task tracker | Проект/issue/task | Приоритеты, доска, родитель, ответственный | Устойчивый ID, структурированные поля, поиск | Три уровня, статусы, фильтры, подробности задачи |
| Coding-agent workspace | Попытка выполнения/branch/workspace | Diff review и предпросмотр | Изоляция рабочего каталога и feedback | Run ID, артефакты и reviewer; execution остается внешним |
| Agent framework | Agent/task/graph/state | Управление автономией и interruptions | Память, tool access, delegation | Actor/role, dependencies, checkpoint references |
| Observability | Trace/span/run/evaluation | Диагностика ошибки и оценка результата | Инструментальные свидетельства | Причина + результат + ссылки на evidence |
| Workflow engine | Event/job/step | Состояние и retry history | Durability, concurrency, idempotency | Транзакции, атомарное владение и устойчивые повторы |
| Development guardrail | Изменение кода | Простота сопровождения | Устранение лишних слоев | Ponytail review с конкретным delete-list |

Сравнение показывает, что продукт не следует сводить к одному из этих классов. Пользователь просит **общую память и контроль работы**, а агенты продолжают писать код в своих штатных средах. Доска отвечает «что запланировано и где застряло», журнал — «что изменили и почему», evidence — «чем подтвержден результат». Эта трехчастная модель является нашим синтезом на основе таблицы, а не заявлением какого-либо отдельного источника.

## Ключевые выводы для архитектуры

### 1. Раздел проекта и статус задачи — независимые оси

В Linear parent/sub-issues, в GitLab work hierarchy и в YouTrack swimlanes работа группируется по смыслу независимо от workflow. Поэтому «Backend», «Подключение агентов» и «Исследование» — разделы проекта, а «Запланировано», «В работе», «Проверка», «Завершено», «Заблокировано» — состояния задачи. Если сделать разделы колонками, пользователь потеряет возможность понять состояние работ в каждом разделе. Если сделать только статусы, потеряет контекст большой задачи.

**Решение:** `project → section → task`; выбранный раздел фильтрует ту же доску по status. Общий обзор проекта включает все разделы. Раздел хранит цель, порядок и архивный признак; прогресс вычисляется из задач, поэтому не создается второй вручную поддерживаемый процент готовности.

### 2. История — часть записи, а не UI-комментарий

Разделение Activity в Jira и versioned description Linear подтверждает полезность разных форм истории. Инструменты наблюдаемости показывают дополнительную ценность run-level details. Применительно к нашему продукту требуется обеспечить целостность события и состояния.

**Решение:** каждое изменение проекта, раздела или задачи автоматически добавляет immutable audit event в той же транзакции. Минимальные поля события: серверное время, тип действия, сущность и ее ID, actor, source (`human`, `codex`, `claude-code`, `api`), `reason`, измененные поля before/after, run/session ID и evidence. Комментарий является самостоятельным событием и не подменяет автоматический diff полей. Исправление ошибочного объяснения добавляет новое событие; прошлое не переписывается.

Система хранит краткую **объявленную причину** действия. Она не обещает раскрывать внутренние рассуждения модели: для аудита нужны цель, принятое решение, альтернативы при необходимости и подтверждение результата.

### 3. Агент выбирает доступную работу и получает атомарное владение

Beads демонстрирует связку ready → atomic claim → close. Workflow engines показывают, почему исполнение с повторами требует concurrency и idempotency. Для нашего продукта это означает, что «assigned to Codex» недостаточно: другой агент может одновременно прочитать ту же задачу.

**Решение:** операция claim выполняется в одной транзакции и проверяет текущего владельца, версию и открытые blockers. Редактирование существующей версионируемой сущности принимает `expected_version`; устаревшая команда возвращает conflict, сохраняя изменения другого участника. Создание и append-only notes используют иной контракт, в частности idempotency key. Зависимости не позволяют циклов и чужих проектных ID. История фиксирует операции владения задачей, предусмотренные окончательным API.

### 4. Успех исполнения и принятие результата — разные состояния

Runs/sessions в AgentOps, LangSmith и workflow engines полезны для диагностики, но один run может завершить только часть задачи. CrewAI и Trigger.dev предусматривают human review/approval. Мы переносим разделение исполнения и проверки без копирования их runtime.

**Решение:** агент переводит задачу в review с итогом и evidence. `done` требует результата проверки либо явного решения пользователя с причиной. Доказательства могут быть конкретными: команда и результат теста, ссылка на commit/PR, путь к артефакту, измерение или описание ручной проверки. Не следует принимать пустое «все проверено» как полноценную запись качества.

### 5. Один контракт для браузера, REST и MCP

Taskmaster использует MCP/CLI, Activepieces переносит typed pieces в MCP, GitHub предоставляет API для Projects. Это подкрепляет API-first интерфейс, но не требует установки агентского framework.

**Решение:** бизнес-проверки находятся на сервере; браузер и MCP вызывают одни операции. MCP дает несколько ясных инструментов для проектов, разделов, задач, claim, событий и сводки. Tools returning JSON должны содержать ID, version и понятные recovery hints. В конфигурации отдельно задается agent identity. MCP-коннектор не требует ключей OpenAI/Anthropic, поскольку не вызывает модели сам.

### 6. Локальное владение данными — важное продуктовое свойство

Текущие сообщения Huly, Vibe Kanban и Flowise показывают, что жизненный цикл готовых платформ меняется. WeKan прямо предупреждает о данных и резервных копиях; export Trello имеет документированную границу истории. Это не означает, что локальное приложение автоматически безопасно: надежность следует сделать проверяемой.

**Решение:** локальный SQLite как достаточное устойчивое хранилище, атомарные изменения, контролируемый путь БД, JSON-экспорт полного проекта с событиями. UI не должен имитировать сохранение посредством одного localStorage. Backup/restore и ограничения удаленного размещения документируются. История в обычном API не удаляется вместе с архивированием задачи.

## Решения по объему реализации с Ponytail

Ponytail нужен как действующий процесс разработки, а не декоративная запись в README. До реализации следует применить его инструкции из исходного репозитория; после реализации независимый reviewer должен пройти созданные изменения и выдать конкретные удаления либо обоснование сохранения. Результат проверки сохраняется в документации проекта.

Для текущего запроса достаточно UI, одного service layer, устойчивой БД и MCP adapter. Специальный event bus, plugin registry, встроенные модели, отдельные микросервисы, собственный терминальный runner и canvas не следуют из требования пользователя. Удаление этих слоев допустимо; удаление validation, transactions, evidence checks, конфликтов версий и accessibility недопустимо. Это применение [Ponytail ladder](https://github.com/DietrichGebert/ponytail#how-it-works) к выявленным требованиям.

## Риски и вопросы, которые исследование не закрывает

1. Для первого локального экземпляра можно использовать одного пользователя и локальные agent identities; многопользовательское удаленное размещение потребует полноценной аутентификации и прав доступа. Локальная метка actor сама по себе не является криптографическим доказательством авторства.
2. Свободный текст evidence не доказывает реальный запуск теста. Поэтому UI должен отличать приложенное свидетельство от независимой проверки reviewer, а документация — ясно описывать этот предел.
3. Ожидаемый размер проекта и число одновременно работающих агентов пока неизвестны. Начальная схема должна иметь pagination/limits и индексы, но масштабный distributed orchestration нельзя оправдать этим неизвестным.
4. Дизайн нужно проверить на реальном основном сценарии: пользователь создает проект; Codex декомпозирует; Claude Code берет доступную задачу; reviewer отправляет замечание; исполнитель исправляет; пользователь читает целую историю. Красивый пустой Kanban не является доказательством готовности.

**Итоговое проектное решение:** создать самостоятельную доску проектов с содержательными разделами, постоянным журналом причин/изменений, проверяемым завершением и узким MCP для внешних coding agents. Это объединяет наиболее полезные механизмы рассмотренных классов, сохраняя простой запуск и понятный пользовательский workflow.
