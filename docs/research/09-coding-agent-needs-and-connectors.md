# Потребности пользователей coding agents и следующие возможности DashAI

Дата исследования: **22 октября 2026, Москва**. Статус: продуктовые рекомендации и план проверки; функции из разделов предложений не реализованы этим исследованием.

## Рекомендация

Следующий этап DashAI — **помочь разработчику сохранять намерение задачи, проверять конкретную версию результата и продолжать работу после смены агента или сессии**.

Первый связный продуктовый пакет: привязка задачи к GitHub PR, результаты CI с точным commit, понятная актуальность evidence, компактный контекст для продолжения и диагностика реального подключения. Следующий коннектор выбирается по рабочему потоку пилотных пользователей: Sentry для исправления производственных ошибок, Linear/Jira для входящих требований, GitLab для команд на GitLab.

Это наша рекомендация на основании источников и аудита. Нет интервью с пользователями DashAI, измеренной частоты проблем, готовности платить или доказанного роста продуктивности. Рынок подтверждает класс потребностей; конкретное решение ещё нужно проверить.

Новые коннекторы не подключались к пользовательским аккаунтам; проверена документация, а не live-совместимость.

## 1. Для кого имеет смысл развивать продукт

Для первого пилота принимаем рабочую гипотезу: **индивидуальный разработчик или технический лидер небольшой команды, который регулярно использует внешних coding agents**. Это соответствует текущей локальной архитектуре; сегмент пользователем пока не подтверждён.

| Сегмент | Работа, которую хочется упростить | Подходящее предложение | Ограничение |
| --- | --- | --- | --- |
| Разработчик с несколькими чатами/клиентами | Вернуться к задаче и продолжить без повторного объяснения | Краткий handoff, решения и проверки со ссылками | Нужна частота повторных сессий; для одного короткого чата ценность может быть низкой |
| Maintainer или solo founder | Принять изменение агента и не пропустить регрессию | PR/CI на точный commit, перечень непроверенных критериев | Зелёный CI не заменяет понимание изменения |
| Техлид небольшой команды | Видеть, где требуется его решение | Очередь исключений и review с происхождением evidence | Локальный DashAI ещё не общий многопользовательский сервис |
| Разработчик существующего продукта | Исправить ошибку, подтвердить исправление после выпуска | Sentry → задача → PR/CI → deployment | Не нужна автоматическая генерация задач по каждому событию |
| Корпоративная команда | Сохранять требования в привычном tracker, учитывать права и политики | GitLab/Jira/Linear; ограниченное чтение выбранных объектов | SSO, RBAC, совместное облачное хранение — отдельный продуктовый и архитектурный объём |

Для обучения новичков и полностью автономной разработки потребуются другие сценарии. Не стоит смешивать их с первым пилотом и делать одну сложную поверхность для всех.

## 4. Какие функции внедрять

### 4.1. Проверяемый результат задачи — первый приоритет

В карточке нужны три различимых факта: **что сообщил исполнитель, что наблюдал источник проверки, что принял проверяющий**. Это подписи и данные о результате, а не обязательные новые Kanban-статусы.

Минимальный сценарий:

1. У задачи указан PR или иной проверяемый результат.
2. У проверки сохранены источник, точный repository/commit или document revision, команда либо run/check ID, результат, время и ссылка на артефакт.
3. Обзор показывает пройденные, проваленные, неприменимые и ещё не выполненные проверки.
4. При появлении нового commit прежний результат остаётся в истории; применимость к текущему изменению становится «требует повторной проверки».
5. Решение review относится к проверенной версии и автору решения. Смена требований тоже должна быть видна проверяющему.

Человеческая/агентная запись с командой и exit code остаётся заявлением автора, пока не получена из независимого наблюдаемого источника. CI доказывает результат указанного job, а не правильность всей задачи. Не требовать GitHub или CI от исследовательской, документной и иной задачи без кода.

Первый прототип можно построить на существующих notes/change и ссылке на PR; для автоматической проверки актуальности понадобится конкретное расширение общего HTTP domain. Не создавать заранее универсальный engine политик и оценок.

**Критерий приёмки:** push B после успешно проверенного A не оставляет впечатление, что B проверен; disabled/skipped/missing checks не становятся зелёным подтверждением. Для документов аналогичная связь с revision.

### 4.2. Передача контекста между сессиями

Рабочее действие: «Подготовить контекст для продолжения». Результат содержит цель, критерии, ограничения, текущую версию результата, принятые решения, последние изменения, неуспешные попытки, оставшиеся проверки и один следующий шаг. У каждого важного утверждения есть ссылка на задачу/note/run и время.

Начать с получения полной note по ID и шаблона handoff поверх существующих notes и краткого экспорта выбранной задачи. Полный текст запрашивается отдельно, с явными лимитами и продолжением при необходимости. Наблюдать, каких сведений систематически не хватает. Только затем добавлять необходимые типизированные поля или составной MCP-read. Полный чат и полный репозиторий в каждый ответ не нужны.

Контекст собирается из явно сохранённых данных; DashAI не должен самостоятельно выдумывать резюме без runtime. Внешний агент может подготовить черновик, человек или следующий агент видит происхождение и актуальность. Пользователь выбирает состав отправки; частные документы и секреты не включаются автоматически.

**Критерий приёмки:** другой клиент объясняет следующий шаг и оставшиеся ограничения, не читая весь предыдущий чат. При отсутствии данных пакет явно сообщает об этом.

### 4.3. Диагностика подключения

Показать отдельные состояния: конфигурация создана; API достижим; авторизация проверена; безопасное чтение выполнено; время последнего успешного запроса. Ошибки 401, 403, 429 и network timeout должны вести к разным действиям восстановления.

Первую проверку сделать read-only: запрос списка/выбранного проекта через реальный MCP-процесс. Не создавать тестовую задачу для проверки каждого подключения. Не писать успешные проверки в бизнес-аудит без изменения данных.

**Критерий приёмки:** пользователь отличает недоступный сервер от отозванного токена и конфиг от реального доступа; диагностический экспорт не содержит credentials.

### 4.4. Очередь внимания на существующей доске

Сохранить существующую выборку «На проверке»; добавить причины внимания «нужно решение», «CI упал», «проверка устарела». Для строки показать причину и точное действие: открыть failed job, перечитать изменение требований, принять результат.

Не строить отдельный notification center до подтверждения необходимости. Одно событие не должно повторно всплывать при каждом poll. Ожидание ввода можно получать из hook поддерживаемого клиента; без такого сигнала нельзя выводить его из last_seen или срока аренды.

**Критерий приёмки:** после возвращения пользователь быстро находит ситуации, где требуется его действие; обычные tool calls не превращаются в поток уведомлений.

### 4.5. Удержание границ задачи и параллельной работы

Сначала использовать существующие description/criteria и документные шаблоны для явных ограничений: что входит в задачу, что исключено, какие зависимости допустимы, что проверять. Показывать изменения требований после начала работы.

Claim сейчас закрепляется за identity, а session ID относится к audit: два чата с одним credential не становятся разными владельцами. Для независимых параллельных исполнителей уже можно использовать отдельные identities. При подтверждённых пересечениях добавить объявленные области работы и предупреждение о похожих затронутых путях. Явно различать заявленный scope и наблюдаемый diff. Это предупреждение, не файловый mutex; управление Git worktrees остаётся в клиенте/IDE. Автоматические блокировки веток, merge и создание worktrees в DashAI пока не обоснованы.

**Критерий приёмки:** два исполнителя видят пересечение до принятия результата; обычный task claim не описывается как защита Git-файлов.

## 5. Коннекторы: приоритет и минимальный объём

Оценки сложности относительные, без обещания сроков. Приоритет отражает соответствие текущему продукту и предполагаемой аудитории, не количественный RICE с выдуманным охватом.

| Коннектор | Пользовательский результат | Минимальная версия и направление | Приоритет / сложность |
| --- | --- | --- | --- |
| **GitHub PR / Checks / Actions** | Понять, какая правка проверена и почему она ещё не готова | Выбранный repo + PR → SHA, checks, statuses, runs и ссылки в DashAI; чтение | **Первый / средняя** |
| **Sentry** | Начать исправление реальной ошибки с контекстом | Выбранный issue → связанная bugfix-задача; project/environment, permalink и безопасная сводка | Следующий для продуктовых разработчиков / средняя |
| **Linear** | Взять реальную задачу без копирования постановки | Импорт выбранных issues одного team/project; remote ID и признак изменения требований | После подтверждения использования Linear / средняя |
| **Jira: входящие задачи** | Использовать существующий tracker как источник требований | Расширение текущей интеграции: чтение выбранной issue, связь с локальной задачей | Может опередить Linear у текущих пользователей / средняя |
| **GitLab MR / Pipelines** | Та же проверка результата для другого Git-провайдера | Выбранный project + MR → SHA и pipeline status | Может стать первым у GitLab-аудитории / средняя |
| **Vercel** | Открыть preview именно проверяемой версии | Deployment выбранного project/SHA → URL, environment и state | После GitHub при web-проектах / малая–средняя |
| **Notion / входящее чтение Confluence** | Передать актуальные требования из внешних документов | Только явно выбранные страницы и ограниченные снимки | Отложить до наблюдения повторного ручного копирования |

### GitHub: конкретный MVP

Официальные API поддерживают [PR][gh-pr], [check runs][gh-checks], [commit statuses][gh-status] и [workflow runs][gh-actions]. Начальные права — чтение необходимых ресурсов выбранных repositories. Fine-grained PAT подходит для личного пилота; GitHub App — отдельный вариант распространения. Не запрашивать merge, rerun или Contents write для чтения результатов.

Хранить стабильные repository/PR IDs, head SHA, фактически проверенный SHA, check/run ID, attempt, conclusion, время наблюдения и URL. При PR workflow проверка может относиться к merge commit: нельзя безусловно считать его равным head SHA. Пустой список checks, merged PR и passed unit test не доказывают выполнение всех criteria.

Ссылки и краткие статусы достаточны для первого опыта. Загрузка всех logs, бинарных artifacts, самостоятельный runner и двусторонний sync issues не входят в MVP. Новый неизвестный SHA или недоступный API должны давать явную неопределённость.

### Sentry: ошибки как вход в рабочий цикл

Актуальное чтение — [organization issues][sentry-issues] с фильтрами project/environment/query и pagination; scope event:read, при проверке проекта может понадобиться project:read. Старый project issues endpoint помечен deprecated. Не включать shortIdLookup, который способен обходить project filter; принадлежность результатов всё равно проверять.

Дедупликация по внешнему issue ID. Пользователь выбирает ошибку, видит preview и создаёт задачу; не плодить карточку на каждое событие. В MVP достаточно названия, количества, first/last seen, окружения и ссылки. Полные requests, breadcrumbs, stack locals и вложения могут содержать секреты/PII и не нужны по умолчанию.

Задача done не закрывает Sentry автоматически. Исправление кода, deployment и прекращение ошибок — разные наблюдения. [Права Sentry][sentry-permissions].

### Linear и Jira: источник постановки, локальное выполнение

Linear имеет [GraphQL API][linear-api], OAuth с [PKCE и read scope][linear-oauth]. При PKCE client secret необязателен, в том числе при refresh: нельзя автоматически закладывать обязательный cloud broker. Регистрацию приложения, callback и согласование прав нужно подтвердить прототипом.

Входящие Linear [webhooks][linear-webhooks] требуют публичный HTTPS non-localhost endpoint. Локальному приложению проще начать с ограниченного исходящего чтения обновлённых issues. Сохранять внешнюю постановку и локальный план как различимые данные, чтобы очередная синхронизация не перезаписала решения агента.

Текущий Jira-коннектор DashAI публикует знания; он не является готовой двусторонней синхронизацией Kanban. Входящее чтение выбранных issues — отдельное расширение. Для Cloud есть [issue API][jira-issues]; Data Center и custom fields требуют своего контракта и проверки. Не обещать одинаковую семантику статусов между разными tracker workflows.

Для возврата итогового комментария позднее понадобятся отдельные права и явная операция отправки. Полный sync всех полей и статусов пока не нужен.

### GitLab, Vercel и документы

[GitLab MR API][gitlab-mr] даёт metadata и pipelines. Для чтения рассмотреть read_api с минимальной ролью и проектной границей. [Project access tokens][gitlab-tokens] на GitLab.com требуют Premium/Ultimate, на Self-Managed/Dedicated доступны при любой лицензии. Личный PAT может иметь более широкую область: закрепление выбранного project необходимо и в приложении.

[Vercel deployments API][vercel-deploy] позволяет искать deployment по project и SHA. READY — сообщение Vercel о deployment, не результат пользовательского теста. [Personal token][vercel-token] с ограничением Team не следует называть гарантированно read-only; у зарегистрированной [integration есть отдельные permissions][vercel-permissions]. Не сохранять bypass secrets и не публиковать закрытый preview.

У Notion есть [Read content capability][notion-capabilities] и выдача доступа выбранным страницам; доступ распространяется на потомков. Это достаточно для небольшого пилота выбранных требований, но не обоснование полного workspace crawler или собственного RAG.

## 6. Не все полезные подключения должны жить внутри DashAI

Есть три разных направления: coding client подключается к DashAI по MCP; DashAI читает внешние факты через сервисный API; сам coding client использует специализированный инструмент. Их не стоит объединять в один универсальный proxy.

| Инструмент внешнего агента | Чем полезен | Что имеет смысл добавить в DashAI |
| --- | --- | --- |
| [Playwright CLI / MCP][playwright] | Работа с браузером и проверка пользовательских сценариев | Краткий рецепт настройки и ссылки на отчёт/скриншот/trace в evidence. Запуск остаётся у агента/CI |
| [Figma MCP][figma] | Контекст компонентов, variables и layout для frontend-задач | Ссылка на выбранный frame/design context, привязка к задаче; без копирования всего файла |
| [Context7][context7] | Документация библиотек с учётом версии | Рекомендуемый источник в workflow; сохранить использованные версию и ссылку в decision |
| [Claude Code hooks][claude-hooks] | События сессии, запрос разрешения/ожидание ввода | Опциональный adapter одного клиента для очереди внимания; явная task/session связь |
| [Usage telemetry][claude-otel] | Наблюдаемые usage/cost/tool metrics поддерживаемого клиента | Рассмотреть позднее, когда нужен контроль расхода; неизвестные значения оставлять неизвестными |

Microsoft отдельно описывает выбор Playwright CLI+skills для компактной работы coding agents и MCP для сценариев с постоянным контекстом браузера. Поэтому требование «всё обязательно через MCP» не обосновано. Наличие инструмента тоже не означает, что тест действительно выполнен.

Figma и Context7 предоставляют контекст, но не гарантируют качество сгенерированного кода. Рекомендованные рецепты — документация со ссылками и проверкой совместимости, без автоматической установки пакетов или доступа к аккаунтам.

Hooks не заменяют task claim или evidence. Сигнал завершения turn не означает завершение задачи; пропавшее событие SessionEnd не доказывает, что агент работает. Полные prompts/tool arguments, личные данные и transcripts не нужны для первой версии диагностики.

## 7. Конкуренты и позиционирование

[GitHub Agent HQ, анонс 04.02.2026][agent-hq] уже описывает работу с несколькими агентами, асинхронные сессии, привязку к issues/PR и review. [Cursor Automations, 05.03.2026][cursor-auto] выполняют облачные агентные задачи по расписанию и событиям. [Linear coding sessions, 11.06.2026][linear-sessions] связывают постановку, облачное исполнение и diff для review.

Это факты о заявленных возможностях на даты публикаций; их качество, тарифы и текущие ограничения здесь не тестировались. Они показывают, что просто «панель для нескольких агентов» уже не сильное самостоятельное отличие.

Перспективная гипотеза позиционирования DashAI: **личное локальное пространство проверяемой работы между разными клиентами, с переносимыми решениями и понятным происхождением результата**. Доказывать нужно экономию ручной сборки контекста и проверки, а не количество подключённых провайдеров.

Для разработчика, полностью удовлетворённого GitHub/Linear и одним агентом, отдельный dashboard может оказаться лишним. Это важный критерий отбора пилота и возможный результат исследования, а не возражение, которое следует скрыть.

## 8. Архитектурные условия

Сохранить один HTTP domain для UI и MCP и одну проектную SQLite. Добавлять конкретный adapter только под выбранный workflow. Повторно использовать существующие patterns версий, idempotency, secrets и outbox там, где они применимы; общий framework заранее не требуется.

Для локального пилота — исходящее чтение по запросу и ограниченный polling активных объектов. [GitHub рекомендует webhooks, а для необходимых REST-запросов описывает conditional requests и соблюдение limits][gh-best]. Локальный polling — компромисс, позволяющий не строить публичный relay. При закрытом приложении обновления не гарантируются; время последнего успеха видно.

Обязательные условия реализации:

- Закреплённые внешние project/repository/page IDs и проверка доступа реальным GET; configuration не равно connection.
- TLS, проверка origin/redirect, лимиты размера/времени, осторожность с self-hosted адресами.
- Credentials вне project store, history, export и диагностических сообщений.
- Локальное изменение данных и audit атомарны. Не создавать business event на каждый неизменившийся poll.
- Внешняя запись, если появится, использует outbox и явные pending/conflict/uncertain; сеть не часть транзакции SQLite.
- Внешний issue/comment/log — недоверенные данные, не инструкции и не разрешение выполнять команды.
- Компактные MCP-ответы и раскрытие деталей по запросу; не отправлять все logs и документы каждому агенту.
- Смена SHA, требований или источника не стирает историю, а меняет применимость прежнего evidence.
- Удаление/отзыв доступа и ошибки не выдаются за пустую успешную синхронизацию.
- UI остаётся доступен с клавиатуры; причина внимания обозначается текстом, а не только цветом.

Граница доверия остаётся локальным пользователем ОС. Имя reviewer или другой agent identity не создают криптографически независимую проверку и корпоративные роли. Для командного SaaS нужен отдельный дизайн доступа, хранения и аудита.

## 9. Последовательность внедрения и готовые кандидаты в backlog

P0 — следующий связный эксперимент; P1 — после результата пилота; P2 — только при подтверждённой потребности. Это предложенные задачи, в реальной доске они не созданы из-за 401.

| Приоритет | Задача и причина | Критерии готовности |
| --- | --- | --- |
| P0 | Диагностика MCP: исправить неоднозначность «конфиг/health/доступ» | Различаются network/401/403; безопасный запрос проверен через MCP; секреты не попадают в вывод |
| P0 | Связать задачу с GitHub PR и прочитать проверки | Repo/PR проверены; точные SHA и источники; pagination/limits; revoked token и offline видны |
| P0 | Показать применимость evidence и предмет review | Новый commit не наследует успех старого; сохраняется история; документные задачи обходятся без обязательного Git |
| P0, малый пилот | Полная note по запросу и шаблон handoff из существующих данных | Длинное решение доступно без потери хвоста; другой клиент получает цель, ограничения, оставшиеся проверки и next step; нет скрытого импорта всего чата |
| P1 | Расширить текущие быстрые выборки причинами внимания | Failed/stale/waiting-review различимы; нет дублей уведомлений и выдуманной активности |
| P1, условно | Один входящий workflow: Sentry либо Linear/Jira | Повторный импорт не создаёт дубль; выбранная область соблюдается; внешние и локальные правки не теряются |
| P2 | GitLab/Vercel/документы/usage по спросу | Каждый коннектор закрывает наблюдённую частую задачу и имеет проверенный источник данных |

Порядок экспериментов:

1. Проверить существующий workflow на недавних реальных задачах и измерить исходное время восстановления/проверки.
2. Сделать один сквозной прототип GitHub → актуальность evidence → review; параллельно дешёвый шаблон handoff.
3. По результатам выбрать следующий источник: ошибки, задачи, второй Git-host или deployment. Не реализовывать всю таблицу одновременно.

## 10. Как проверить пользу с пользователями

Предлагаемый пилот: 8–12 разработчиков с реальными репозиториями, минимум две группы — solo/multi-client и разработчики существующих продуктов. Среди них нужны пользователи, которым текущие инструменты уже удобны; иначе исследование переоценит спрос.

Сначала попросить показать последние 2–3 реальные задачи: смену сессии, проблемный review, CI failure или ошибку подключения. Выяснять действия и затраты, а не спрашивать «нравится ли коннектор». Не собирать приватные transcripts и production data без необходимости.

Для прототипа дать три задания:

1. Определить, относится ли приложенная проверка к последней правке; специально включить новый commit после старого зелёного CI.
2. Передать незавершённую задачу другому агенту/клиенту и назвать следующий шаг.
3. Разобраться с невалидным токеном и восстановить доступ без копирования секрета в чат/отчёт.

Метрики: время до правильного решения review; доля ошибочного доверия старому evidence; время до осмысленного следующего шага; число ручных повторных объяснений; время настройки/восстановления; повторное использование через две недели. Для coding tasks дополнительно учитывать reopen/rework и ожидание CI. Не считать секунды между audit events активным трудом человека.

Предварительные пороги решения, которые следует согласовать до пилота: не менее 80% участников правильно замечают устаревшую проверку; медиана времени проверки снижается хотя бы на 20% без роста ошибок; handoff позволяет большинству продолжить за две минуты; минимум половина добровольно повторяет сценарий на следующей неделе. Это критерии эксперимента, **не прогноз и не достигнутые результаты**. Маленькая выборка не даёт оснований заявлять статистически доказанный эффект для рынка.

Если ссылок на PR и существующего GitHub UI достаточно — остановиться на лёгкой связке. Если handoff не улучшает восстановление — оставить шаблон и не строить новую модель памяти. Если второй tracker создаёт двойное ведение — перейти к ссылкам и чтению выбранных задач.

## 11. Что пока не внедрять

- Собственный runtime моделей, chat/terminal IDE, общий orchestrator и auto-merge/deploy.
- Двустороннюю синхронизацию всех полей всех trackers.
- Universal connector SDK, marketplace исполняемых плагинов и публичный webhook relay без конкретного спроса.
- Полный transcript collector, vector database и RAG поверх всех источников.
- Предсказанные «часы экономии», confidence score, рейтинг агентов или разработчиков по tokens/LOC/events.
- Обязательный корпоративный approval для каждой задачи только потому, что код написал агент.
- Полноценный cost dashboard до наличия надёжного источника usage и правил учёта подписки/кэширования.
- Автоматические файловые блокировки на основании task claim.

## 12. Решение на следующую итерацию

Рекомендуется проверить **GitHub + актуальность evidence + handoff + диагностику MCP** как один небольшой рабочий цикл. Именно он добавляет новый наблюдаемый результат к существующим сильным сторонам DashAI.

Sentry, Linear/Jira, GitLab и Vercel остаются конкретными следующими кандидатами, но их порядок должен определиться реальными рабочими потоками первых пользователей. Результат этого исследования — приоритеты и проверяемые гипотезы; реализация и подтверждение спроса ещё впереди.
