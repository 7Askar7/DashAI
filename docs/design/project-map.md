# Карта проекта: дерево объяснений и архитектура

Дизайн-концепция от 16.10.2026. Статус: прототип для обсуждения. [Открыть прототип](project-map.html). Его можно открыть обычным браузером как локальный HTML-файл; сервер и установка зависимостей не нужны.

Рабочая реализация 1.5.0 и её границы описаны в [project-map.md](../project-map.md). Ниже сохранена спецификация прототипа; формулировки «следующий этап» относятся к моменту его создания.

## Задача

Человек открывает проект и понимает, что делает каждый файл, как он работает, зачем нужен и с чем связан. Названия и вложенность повторяют репозиторий, но выбор файла открывает объяснение обычным языком. Второе представление показывает архитектуру и возвращает к описаниям соответствующих файлов.

Прототип использует часть реальной структуры DashAI и подготовленные пояснения. Это примеры дизайна, а не результаты подключённого генератора, полная инвентаризация репозитория или подтверждение актуальности исходников. Данные рабочего приложения не читаются и не изменяются.

## Экраны

**Файлы и описания.** Слева дерево и поиск по пути, названию и содержанию объяснения. Справа путь, название файла, его роль, краткое описание, «Зачем нужен», «Как работает», связанные файлы и переход к блоку архитектуры. Папки раскрываются обычными disclosure-контролами; выбор файла не запускает редактор кода. В рабочей версии выбор папки открывает её назначение и обзор вложенных частей; в прототипе папки только раскрывают дерево.

**Архитектура.** Небольшая схема компонентов с подписанными направлениями обращений. Выбор блока открывает его роль, связи и файлы. Выбор файла возвращает в дерево. Для DashAI схема показывает UI → HTTP API → SQLite и внешний агент → MCP → HTTP API. Код работы с SQLite находится в `server/app.py`; отдельный блок хранения не означает отдельный исходный модуль. Схема намеренно не охватывает packaging, desktop runtime и обновления.

### Нотации и вопросы читателя

Переключатель «Представление / нотация» сохраняет свободный обзор и добавляет семь подготовленных схем. Это разные представления и уровни одной системы; смена названия не подменяет изменение структуры схемы.

| Представление | Какой вопрос закрывает | Содержание |
| --- | --- | --- |
| C4 L1 · Контекст | Кто использует систему и зачем? | Человек, DashAI как одна система, внешние клиенты |
| C4 L2 · Контейнеры | Какие приложения и хранилище образуют систему? | Граница DashAI, UI, API, MCP, SQLite, технологии и протоколы |
| C4 L3 · Компоненты API | Как организована внутренняя ответственность сервера? | HTTP-обработчики, actor, правила изменений, Store внутри контейнера API |
| UML Sequence | В каком порядке участники обмениваются сообщениями? | Успешный claim_task через MCP, HTTP API и SQLite; линии жизни, запросы и ответы |
| UML State | Как задача проходит обычный рабочий маршрут? | Состояния, переходы и условия; это типичный сценарий, не полный автомат API |
| ERD | Какие сущности связаны и с какой кратностью? | Project, Task, Note, Event, Agent; логическая модель, не физическая схема БД |
| Flowchart | Где возникает ветвление алгоритма? | Проверка версии, конфликт 409, повторное подтверждение, сохранение или откат |

У каждого представления есть название, цель, область, легенда, текстовое объяснение и исходные файлы. Смысл передаётся типами, подписями и линиями, а не только цветом. На узком экране двумерная схема сохраняет отдельную горизонтальную прокрутку с клавиатуры; текстовое объяснение остаётся читаемым без неё. Свободный обзор по-прежнему переходит в список блоков на телефоне.

C4 не требует конкретной графической нотации; в прототипе используются подписанные типы элементов и границы. Компоненты L3 не означают новые процессы или файлы: всё показанное находится в `server/app.py`. ERD показывает только часть логических связей, исключая credentials. Sequence иллюстрирует успешный сценарий; Flowchart отдельно поясняет ошибку версии и отказ проверок. UML-представления покрывают эти конкретные диаграммы, а не весь UML. BPMN и полноценный визуальный редактор не заявляются.

### Сборка документации

Третья вкладка «Документация» позволяет изменить название и контекст, выбрать разделы и схемы, прочитать предпросмотр и скачать результат. Разделы: цель/границы, архитектура/сценарии, описания файлов, краткие принятые решения, проверки/ограничения. Это компактная структура для прототипа, не полный шаблон arc42 и не готовый журнал ADR.

Из архитектуры кнопка «Включить в документ» добавляет выбранную схему без дублей и включает соответствующий раздел. При исключении раздела или схемы предпросмотр и экспорт обновляются из одного состава. Авторский ввод отображается как текст; HTML в нём не исполняется. Выбор хранится в памяти текущей вкладки и не записывается в project store; интерфейс предлагает скачать документ до закрытия.

- **Markdown:** объяснения, области, легенды, файлы и выбранные схемы в блоках Mermaid. Для отрисовки нужен Markdown-просмотрщик с поддержкой Mermaid.
- **HTML:** самостоятельный файл со встроенными SVG, стилями и развёрнутыми описаниями файлов; не требует сервера, внешних ресурсов или скриптов.
- **Печать / PDF:** системный диалог печати браузера с возможностью сохранить PDF. Навигация/настройки скрыты, описания файлов раскрываются на время печати и затем восстанавливаются. Это не отдельный серверный генератор PDF.

У каждой схемы можно открыть и скачать исходник `.mmd`. Для C4 используются `flowchart` с типами и границами, для остальных — `sequenceDiagram`, `stateDiagram-v2`, `erDiagram` и `flowchart`. В прототипе SVG-предпросмотр подготовлен отдельно от Mermaid; изменения исходника не редактируют картинку. Версия полноценного продукта должна генерировать представления и экспорт из общей опубликованной модели со снимком исходников.

Описания, новые схемы и экспорт явно обозначены подготовленными примерами. Скачивание действительно работает, но не подтверждает полноту, актуальность или проверенность документации реального проекта.

Первичные руководства: [уровни C4](https://c4model.com/diagrams), [типы, подписи и легенда C4](https://c4model.com/diagrams/notation), [контейнеры C4](https://c4model.com/diagrams/container), [Mermaid Sequence](https://mermaid.js.org/syntax/sequenceDiagram.html), [Mermaid State](https://mermaid.js.org/syntax/stateDiagram.html), [Mermaid ERD](https://mermaid.js.org/syntax/entityRelationshipDiagram.html), [Mermaid Flowchart](https://mermaid.js.org/syntax/flowchart.html), [структура arc42](https://arc42.org/overview/). Сверены 16.10.2026; графика и текст примеров созданы для DashAI.

Сохраняются существующие тёмные поверхности, типографика и зелёный акцент DashAI. Дерево занимает около 264 px; основная площадь отдана чтению. У архитектуры вспомогательная панель справа, которая на меньшей ширине переходит вниз. На телефоне дерево сворачивается после выбора файла, а схема становится читаемым списком блоков с текстовыми связями. Все действия доступны с клавиатуры; цвет дополнен текстом, поддержано уменьшение движения.

## Состояния

В прототипе переключатель «Пример состояния» позволяет посмотреть черновик, устаревшее описание, отсутствие описания, ожидание результата и ошибку. Смена состояния ничего не генерирует и не сохраняет.

| Состояние | Поведение рабочего продукта |
| --- | --- |
| Нет описания | Объяснить следующий шаг: запросить анализ выбранного файла или папки |
| Черновик ИИ | Показать автора, время и исходную ревизию; дать прочитать и проверить |
| Проверено | Привязать решение проверяющего к конкретной версии описания и исходника |
| Требует обновления | Сохранить прежний текст, указать изменение исходника и предложить обновление |
| Создаётся | Показать реальное состояние запроса; разрешить продолжить навигацию |
| Ошибка | Сохранить прежний результат, объяснить сбой и предложить повтор |
| Репозиторий недоступен | Объяснить, что путь не найден или нет доступа; не выдавать снимок за живое подключение |
| Ничего не найдено | Сохранить поисковый запрос и дать его изменить или сбросить |

«Проверено» не равно «ИИ написал»; соответствие описания коду не подтверждается только фактом получения текста. Статус актуальности также не равен состоянию подключения агента.

## Как ИИ создаёт содержимое

Предлагаемый процесс, ещё не реализован:

1. Человек связывает проект с репозиторием и выбирает область анализа.
2. Внешний Codex/Claude Code в своей среде читает разрешённые исходники. DashAI не добавляет runtime моделей или ключи провайдера.
3. Агент передаёт через MCP структурированные описания файлов/папок и явно обозначенные связи компонентов в общий HTTP API.
4. Сервер проверяет проект, относительные пути, объём, ссылки и версии; сохраняет результат и audit event одной транзакцией в существующем project store.
5. ИИ-текст становится черновиком. Человек проверяет его или агент обновляет после изменения исходника.

Кнопка «Запросить обновление» в рабочем продукте должна создавать реальный запрос/задачу. Наличие MCP-конфига не означает, что агент исполняет запрос; до подтверждения исполнения используется «Ожидает агента». Конкретный механизм доставки запроса внешнему агенту ещё требует реализации. Существующие `log_change` и время последнего обращения не доказывают, что весь репозиторий просканирован.

Минимальные данные описания: project ID, относительный путь, тип элемента, текст назначения, объяснение работы, причина существования, связанные пути, автор, время, версия описания, идентификатор анализированного снимка и hash исходного файла. Отдельно фиксируется проверка текста. Commit недостаточен для незакоммиченных изменений; нужен снимок с hashes. Для архитектурных узлов и связей нужны ссылки на описанные пути и тот же снимок. Выбор физической схемы хранения отложен до реализации общего API.

Актуальность определяется сравнением доступных снимков исходников. Пока нового снимка нет, UI показывает дату последнего анализа и «Изменения после анализа не проверены». После сверки изменённые файлы получают «Требует обновления», удалённые остаются в истории. Автоматический watcher не требуется для первого этапа.

Из проекта исключаются credentials, `.env`, приватные данные, `.git`, зависимости и результаты сборки; правила исключения учитываются при первом анализе. Агент не загружает их в описания или audit. Пути ограничены выбранным корнем, включая symlink/junction; документ нельзя использовать для произвольного чтения файлов. Сгенерированное содержимое отображается как текст/безопасный Markdown, без исполняемого HTML. Конкурентные изменения используют `expected_version`; stale overwrite запрещён. Новый MCP-метод обращается к HTTP API, а не создаёт отдельное хранилище.

## Следующий этап реализации

Сначала добавить хранение и общий HTTP/MCP-контракт описаний и снимков, затем привязать дерево к опубликованному агентом снимку и встроить чтение в проект DashAI. Архитектура использует те же описания и связи. Успех первого этапа: агент передал описание, человек открыл его из дерева, перезапустил приложение и получил ту же версию с автором и историей. Изменённый снимок помечает устаревшие документы; конфликт не затирает чужую правку.

Не нужны на этапе дизайна: новые библиотеки графов, встроенный запуск моделей, автоматический разбор всех языков, отдельная база коннектора или редактирование кода. Масштабирование схемы, детальные уровни архитектуры и выбор механизмов анализа решаются после проверки основного сценария.
